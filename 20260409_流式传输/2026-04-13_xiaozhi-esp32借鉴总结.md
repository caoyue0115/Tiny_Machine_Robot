# xiaozhi-esp32 借鉴总结与本项目下一步建议

日期：2026-04-13

参考项目：https://github.com/78/xiaozhi-esp32

本文件只总结对当前“宗教大模型云服务器 Demo + ESP32-S3 板端”有直接价值的设计点。结论先行：小智项目最值得借鉴的是 **Opus 音频传输、音频任务解耦、唤醒/聆听/播报状态机、VAD 动态结束、资源资产管理**。不建议当前会展版本直接搬迁到它的完整 WebSocket/MQTT+UDP/C++ 框架。

## 0. 当前实现状态澄清

为避免把“已做完”和“建议后续做”混在一起，先明确当前代码状态：

- 板端**已经有轻量能量 VAD**，实现是“最长 `4s` + 提前结束”，不是死录满 `4s`。
- 当前**还没有**“唤醒后等待用户开口”的完整动态等待状态机；也就是说，还没有 `ListeningPending / ListeningSpeech / ListeningEnding` 这套交互。
- 当前云端 **Opus 已支持且可通过 feature flag 开启**，但仍保留 `PCM` fallback。
- 当前**不存在**“同一次会话中静默从 `v3_stream` 自动切到 `v2_preload`”的 fallback；`v2/v3` 仍应在会话开始前选择。

因此，本文件中提到的 “VAD 动态结束” 有两层含义：

- 已完成：轻量能量 VAD 提前结束录音。
- 未完成：完整动态等待状态机 + 无语音不上传 + 等待用户开口。

## 1. 当前问题判断

当前板端已经直连 Wi-Fi，上海公司网络重测后结果明显改善：

- Ping：30 次丢 1 次，丢包约 3%，平均 41ms，最大 48ms。
- HTTP：30 次全部成功，平均 116ms，最大 205.3ms，jitter 114.2ms。

这说明“公司电脑到香港阿里云”的基础链路已经比之前 20% 丢包、HTTP 长尾 1.97s 的状态好很多。但板端真实链路仍然更脆弱：ESP32-S3 只支持 2.4GHz，天线、AP 拥塞、手机热点中继、会展现场干扰都会放大 `max_gap_ms` 和 `underrun_count`。

因此后续不能只靠云端或 PC 侧测速判断，需要持续记录：

- 板端 `first_audio_byte_local_ms`
- 板端 `max_gap_ms`
- 板端 `underrun_count`
- 板端 `underrun_ms`
- `/audio` 首包、总字节、分块最大间隔
- 当前选择的链路模式：`v3_stream` / `v2_preload`

## 2. 小智项目值得借鉴的设计

### 2.1 Opus 作为音频传输格式

小智 WebSocket 协议的 `hello` 明确声明音频参数：

```json
{
  "type": "hello",
  "version": 1,
  "features": {"mcp": true},
  "transport": "websocket",
  "audio_params": {
    "format": "opus",
    "sample_rate": 16000,
    "channels": 1,
    "frame_duration": 60
  }
}
```

服务端也可以通过 `hello` 返回下行音频参数，例如 `format=opus`、`sample_rate=24000`、`frame_duration=60`。

对当前项目的意义：

- 当前下行 PCM 约为 `24000Hz * 16bit * 1ch = 48KB/s`，8 秒回答约 384KB。
- Opus 语音常见码率可压到约 16-32kbps，实际传输量通常可降低一个数量级。
- Opus 能明显降低弱网下的下载压力，但它不能解决 TTS 供应商本身的“生成长尾”或服务端分段间隔问题。
- Opus 上线必须保留 PCM fallback，否则板端解码、帧边界、采样率协商任一环出问题都会影响演示。

建议本项目不要第一步就切 WebSocket。更稳妥的路径是：**保留当前 HTTP chunked v3 `/audio`，先把 payload 从 PCM 可选切成 Opus 帧流**。

建议新增协商/响应头：

```http
X-Audio-Format: opus
X-Opus-Sample-Rate: 24000
X-Opus-Channels: 1
X-Opus-Frame-Duration-Ms: 60
```

帧格式可先用简单长度前缀，避免裸 Opus 包边界不清：

```text
uint16_be payload_len + opus_payload
uint16_be payload_len + opus_payload
...
```

### 2.2 音频任务解耦

小智 `AudioService` 的核心结构是队列化：

- `AudioInputTask`：采集麦克风 PCM。
- `AudioProcessor`：AEC/NS/VAD 等语音处理。
- `OpusCodecTask`：统一处理 Opus encode/decode。
- `AudioOutputTask`：只负责播放 PCM。
- 网络层与播放层通过 decode/playback queue 解耦。

对当前项目的意义：

- 当前 v3 下行逻辑更像“网络收到 chunk 后 callback 直接喂播放队列”。这已经能跑，但弱网或播放写入慢时，网络、解码、播放的责任边界不够清楚。
- 借鉴小智后，可以把链路拆成：`HTTP receive task -> frame/decode queue -> PCM jitter queue -> I2S output task`。
- 这样更容易定位卡顿来自网络间隔、Opus 解码耗时、队列阻塞还是 I2S 播放。

当前已经加过 `realtime_audio_enqueue_slow` 和 close wait 日志，下一步可以继续把这些指标固化到队列层。

### 2.3 唤醒后的状态机

小智的 `Application` 有明确状态：

- `Idle`
- `Connecting`
- `Listening`
- `Speaking`
- `WifiConfiguring`
- `AudioTesting`

唤醒词触发后，不是简单录固定 4 秒，而是：

- Idle 时打开音频通道。
- 可发送唤醒词附近的音频片段。
- 发送 `listen detect`。
- 进入 listening mode。
- 如果播报中再次唤醒，则 abort 当前 speaking/listening，再重新进入 listening。

对当前项目的意义：

- 领导提出的“动态等待用户发问”本质上需要状态机，而不是一个固定 `record 4s` 的流程。
- 当前触屏触发也可以先映射成同样的状态：`Idle -> Prompting -> Listening -> Uploading -> StreamingAudio -> Idle`。
- 之后提示词唤醒、触摸唤醒、物理按钮唤醒都进入同一套状态机，避免分叉逻辑越来越多。

### 2.4 VAD 动态结束

小智的 `AfeAudioProcessor` 使用 ESP-SR AFE，并在 `fetch` 结果里处理 VAD 状态变化：

- `VAD_SPEECH`：认为用户开始说话。
- `VAD_SILENCE`：认为用户停止说话。
- 输出固定帧长的音频给编码/发送队列。

对当前项目的意义：

- 当前项目已经有“轻量能量 VAD 提前结束”，所以这里不是从 `0` 到 `1` 的补课，而是从“提前结束录音”继续升级到“完整动态等待交互”。
- “动态等待”至少需要两个阶段：等待用户开始说话、检测用户说完。
- 不能只用“启动后 4 秒结束”，否则用户还没开始说就上传空音频，或者用户话没说完就截断。
- 如果当前先不接 ESP-SR，也可以做一个简化版能量 VAD：短时能量超过阈值视为 speech，连续静音超过阈值视为 end。

建议动态等待参数初版：

| 参数 | 建议值 | 说明 |
| --- | --- | --- |
| `wait_speech_start_ms` | 6000-8000 | 唤醒后最多等用户多久开口 |
| `min_speech_ms` | 500-700 | 防止短噪声触发 |
| `end_silence_ms` | 800-1200 | 用户说完后的静音判定 |
| `max_utterance_ms` | 10000-12000 | 防止一直占用 |
| `no_speech_action` | 本地提示“我在听，请再说一遍” | 不上传空音频 |

### 2.5 唤醒词/提示词音频缓存

小智 `AfeWakeWord` 会保留约 2 秒唤醒词附近 PCM，并可异步编码成 Opus 包发送。

对当前项目的意义：

- 如果后续做真正唤醒词，而不是触摸按钮，建议保留“唤醒前后 1-2 秒”音频缓存。
- 这样用户说“你好小智，佛教怎么看无常”时，不会只录到“佛教怎么看无常”，也不会漏掉唤醒后的前几个字。
- 对提示词唤醒尤其重要，因为用户往往不会在唤醒音结束后才规整开口。

### 2.6 本地提示音资源管理

小智把一些提示音做成 OGG/Opus 资源，例如 `popup.ogg`、`success.ogg` 等，并有 assets 分区/资源加载机制。

对当前项目的意义：

- 当前开场音失败主要不是仓库缺资源，而是板子没有正确刷 SPIFFS `storage.bin` 的风险更大。
- 当前 `intro_1.pcm` 是 raw PCM，占用大、不可自描述。后续可以把本地提示音统一成 Opus/OGG 资源，板端统一走解码播放队列。
- 短期先确保 SPIFFS 被刷入，启动日志 `SPIFFS used != 0`，且没有 `/spiffs/intro_1.pcm` 打开失败。

## 3. 不建议当前直接照搬的部分

### 3.1 不建议立即迁移到完整 MQTT+UDP

小智支持 MQTT 控制 + UDP 加密音频，这是更完整的实时语音架构：控制面和数据面分离，UDP 包有 sequence/timestamp/ssrc，并做 AES-CTR 加密。

但当前不建议直接做，原因：

- 需要服务端协议重写和部署改造。
- 会展网络、NAT、防火墙环境下 UDP 可能更不稳定。
- 调试复杂度显著上升，不适合在现有卡顿问题未完全归因时引入。

可以作为中长期方向，但不进入本轮会展稳定化主线。

### 3.2 不建议整体迁移到小智 C++ 框架

小智是完整产品级 C++ 架构，Board/Application/Protocol/AudioService 都有自己的抽象。当前项目是更直接的 C/HTTP demo 架构。

直接迁移风险：

- 触摸、屏幕、I2S、SPIFFS、云端 API 都要重接。
- 已经打通的 v2/v3 逻辑会被大范围扰动。
- 短期回归成本高于收益。

正确方式是“借设计，不搬框架”。

### 3.3 不建议一开始就做完整 ESP-SR 自定义唤醒词

ESP-SR 唤醒词需要模型资源、分区、内存、PSRAM、AEC/VAD 参数一起验证。它值得做，但应作为独立 spike，不应和 Opus、动态等待、开场音并行混做。

短期可以先实现“提示词/触摸触发后的动态等待”，等主链路稳定后再接真实 wake word。

## 4. 对用户当前 5 点计划的判断

### 4.1 下载小智并总结可借鉴内容

已完成本总结。建议把小智作为架构参考，而不是作为直接依赖。

### 4.2 音频传输用 Opus 而不是 PCM

方向正确，但建议分两步：

1. **先做下行 Opus**：服务端 TTS 输出后编码 Opus，v3 `/audio` chunked 返回 Opus 帧，板端解码成 PCM 播放。
2. **再做上行 Opus**：板端录音从 PCM 上传改为 Opus 上传，服务端解码后走 ASR。

原因：当前主要卡顿在语音返回，下行 Opus收益最大；上行录音短，先动下行更稳。

必须保留：

- `audio_format=pcm` fallback。
- 板端日志打印下行格式、Opus 帧数、解码失败数、decode max ms。
- 云端日志打印编码耗时、Opus bytes、PCM bytes、压缩比。

### 4.3 开场声音与 `/audio` 并行

方向正确。建议状态机改成：

```text
session accepted
  -> start local prompt playback
  -> immediately start /audio request in background
  -> cloud audio arrives: only入队/缓存，不抢播
  -> local prompt done
  -> start cloud jitter prebuffer
  -> play cloud audio
```

关键点：

- 本地提示音不要阻塞 `/audio` 请求，否则首包等待被人为拉长。
- 云端音频先缓存，不要和本地提示音混播。
- 本地提示音控制在 0.8-1.5 秒，过长会让用户感觉慢。
- 如果云端先失败，本地提示可以接“网络不稳定，请稍后再试”的缓存音。

### 4.4 提示词唤醒 + v2/v3 双链路

方向正确，但建议把“双链路”定义成策略，不是自动乱 fallback：

- `v3_stream`：网络质量好时使用，体验更实时。
- `v2_preload`：网络质量差、会展现场拥塞、或某些提示词路径需要稳定播完时使用，先完整生成/下载再播放。

建议选择条件：

| 条件 | 建议链路 |
| --- | --- |
| 最近 3 次 v3 `underrun_count=0` 且 `max_gap_ms < 500` | v3 |
| 当前 HTTP healthz 连续长尾 > 800ms | v2 |
| 板端最近一次 `max_gap_ms > 1000` 或 `underrun_count > 0` | v2 |
| 会展现场 2.4G 明显拥塞 | v2 |
| 需要“必须完整播完”的固定引导/讲解 | v2 |

用户之前确认过“v3 失败不要自动 fallback v2”。这里建议保持这个原则：**不要在一次会话中静默 fallback**。可以在会话开始前根据网络评分选择 v2 或 v3，并把选择原因打日志。

### 4.5 唤醒后动态等待用户发问

这是必须改的交互点。建议优先级高于 Opus，因为它直接影响领导体验。

建议交互：

```text
Idle
  -> wake/touch detected
  -> play local prompt: “请问。”
  -> ListeningPending: 等用户开始说话，最多 6-8 秒
  -> ListeningSpeech: 检测到说话后持续录
  -> ListeningEnding: 连续静音 0.8-1.2 秒后结束
  -> Uploading/ASR
  -> StreamingAudio 或 PreloadAudio
  -> Idle
```

无语音时不要上传保底 4 秒空音频，改为：

- 第一次无语音：本地提示“我在听，请再说一遍。”
- 第二次仍无语音：回到 Idle。

## 5. 建议的分阶段落地计划

### Phase 0：继续固化当前 v3 诊断

目标：确认板端直连 Wi-Fi 后真实卡顿是否还存在。

动作：

- 每次联调记录 `ping 丢包率`、HTTP 30 次长尾、板端 `max_gap_ms`、`underrun_count`。
- 刷机时确认 SPIFFS `storage.bin` 已刷入。
- 观察新增日志 `realtime_audio_enqueue_slow` 和 close wait 日志。

验收：

- `underrun_count=0`。
- `max_gap_ms < 500ms`，理想 < 200ms。
- 播放结束后状态能回 Idle，触屏不再出现 pipeline busy 卡死。

### Phase 1：动态等待 + 开场音并行

目标：先把交互体验修正，不引入编解码大改。

动作：

- 实现 `Idle/Prompting/ListeningPending/ListeningSpeech/Uploading/StreamingAudio/Idle` 状态机。
- 录音结束从固定 4 秒改为 VAD/能量动态结束。
- `/audio` 请求与本地 prompt 并行，云端音频先缓存。

验收：

- 用户唤醒后晚开口 3-5 秒仍可正常识别。
- 用户短问句不被截断。
- 无人说话不上传空音频。
- 开场音存在时 `first_audio_byte_local_ms` 不被本地播放人为拖慢。

### Phase 2：v3 下行 Opus feature flag

目标：降低弱网下行带宽和卡顿概率。

动作：

- 服务端增加 `audio_format=opus` 输出。
- 板端增加 Opus decoder 和帧解析。
- 默认仍可切回 PCM。
- 日志增加 Opus 帧数、解码耗时、解码失败数、压缩比。

验收：

- 同一回答下行 bytes 至少下降 5 倍。
- 板端 Opus decode max 耗时低于单帧时长的 30%。
- 弱网下 `underrun_count` 比 PCM 明显下降。
- PCM fallback 可用。

### Phase 3：提示词唤醒 + v2/v3 模式选择

目标：为会展现场准备稳定模式。

动作：

- 把触摸触发和提示词唤醒统一接入状态机。
- 增加会话前网络评分。
- 好网络走 `v3_stream`，坏网络或固定讲解走 `v2_preload`。
- 每次会话日志打印 `selected_path` 和 `selected_reason`。

验收：

- 网络差时不会边播边卡，而是先预加载再播。
- 网络好时仍保留 v3 实时体验。
- 不发生一次会话中静默从 v3 切 v2 的不可解释行为。

### Phase 4：再评估 WebSocket / MQTT+UDP

目标：产品化时再考虑更完整实时协议。

当前不建议进入会展版本主线。

## 6. 额外建议

### 6.1 会展现场优先准备网络 B 计划

即使改 Opus，2.4GHz 会展现场仍可能抖动。建议准备：

- 独立 2.4GHz 路由器，尽量少设备接入。
- 服务器尽量靠近现场网络路径，必要时准备大陆/华东节点。
- 现场开场前跑 3 轮板端实测，不只跑电脑测速。
- 保留 `v2_preload` 展示模式，牺牲一点实时感换稳定播完。

### 6.2 本地缓存更多兜底提示音

建议板端缓存：

- “请问。”
- “我在听，请再说一遍。”
- “网络有些不稳定，请稍后再试。”
- “正在思考。”

这些短音频最好后续统一用 Opus/OGG，而不是 raw PCM。

### 6.3 指标口径要固定

后续评估不要只说“卡/不卡”，每次至少给：

```text
network: ping_loss, http_avg_ms, http_max_ms
board: first_audio_byte_local_ms, max_gap_ms, underrun_count, underrun_ms
server: first_audio_ms, audio_max_chunk_gap_ms, production_ratio
mode: v3_stream or v2_preload
```

### 6.4 Opus 不是唯一答案

Opus 能解决“带宽压力”，但不能单独解决：

- TTS 供应商首包慢。
- 服务端生成中途断档。
- 板端播放任务被其他任务抢占。
- SPIFFS 没刷导致本地音失败。
- 状态机没有回 Idle 导致触屏 busy。

所以 Opus 应和状态机、动态等待、队列日志一起推进。

## 7. 推荐当前执行顺序

1. 先跑一次板端直连 Wi-Fi 的完整 v3 实测，记录 `max_gap_ms/underrun_count/first_audio_byte_local_ms`。
2. 修动态等待，去掉固定 4 秒保底录音作为默认路径。
3. 修开场音与 `/audio` 并行，但云端音频要等本地 prompt 结束后再播。
4. 做 v3 下行 Opus feature flag，保留 PCM fallback。
5. 做会话前模式选择：网络好走 v3，网络差或会展保稳走 v2 预加载。
6. 最后再评估真正 ESP-SR 唤醒词和 WebSocket/MQTT+UDP。

这个顺序的原则是：先修交互确定性和可观测性，再降低带宽，最后做协议和唤醒词大改。
