### 3.3 这轮新增的排障原则

- 不要再仅凭 `audio_format=pcm` 就怀疑 header 格式错误。
  - 必须先确认：
    - 板端版本是否是最新
    - 公网实例是否已部署最新代码
    - 远端 feature flag 是否真的开启
- 当怀疑“部署没生效”时，优先做**同一 session 的双地址交叉验证**：
  - `127.0.0.1` 创建 -> `OLD_PUBLIC_ENTRY_DISABLED` 读取
  - `OLD_PUBLIC_ENTRY_DISABLED` 创建 -> `127.0.0.1` 读取
- 如果双向都 `404 session_not_found`，优先结论应是：
  - **不是协议问题**
  - **不是板端 header 问题**
  - 而是实例/部署路径不一致
- 以后所有“公网已切新代码”的结论，至少要满足两条：
  1. 远端容器内检查：
     - `opus_available`
     - `realtime_audio_enable_opus`
  2. 公网 smoke 明确看到：
     - `audio_format=opus`
     - `audio_packetization=framed-v1`

## 17. 2026-04-12 bug18 v6 日志结论

`bug18_1.txt` 是完整三轮日志，`bug18_2.txt` 是问五六轮后出现语音停止、没有任务结束、触摸无效的日志。这两份日志属于 v6，还没有合入 bug16 的两个防护。

结论分两层：

- 卡顿层面：v6 日志确实证明播放端发生欠载。多轮 `realtime_audio_summary` 的 `underrun_count` 和 `underrun_ms` 很高，且 `max_inter_chunk_gap_ms` 可到数秒，说明当时上游 PCM chunk 供给不均，播放速度会阶段性超过生产/到达节奏。
- 卡死层面：`bug18_2` 最后一轮已经打印 `stage=stream_audio event=done` 和流统计，但没有 `Realtime jitter playback task done`、没有 `realtime_audio_summary`、没有 `pipeline task finished`。这说明不是容量用完，而是卡在 stream 结束后的 jitter 播放任务收尾/close 阶段。

已确认代码根因：

- `audio_stream_task` 旧逻辑要求 `scratch_len == 0` 才能退出。
- 如果最后一个 PCM chunk 非 `1024` 对齐，例如 `last_chunk_bytes=1536`，会留下 `512` 字节在 `scratch_len`。
- 流结束后无新 ringbuffer item，旧逻辑不会 flush 这个尾包，也不会退出，导致 close 永久等待，主状态不回 idle，触摸无效。

修复状态：

- `audio_stream_task` 现在只要流已停止且 ringbuffer 水位为 `0` 就退出循环。
- 退出循环后会执行已有的 `if (scratch_len > 0)` 尾包 flush。
- 文本回归 `python -m unittest tests.test_esp_runtime_guards tests.test_esp_assets` 已覆盖该风险。
- `idf.py build` 通过，app binary `0xfac30`，2MB app 分区剩余约 `51%`。

### 27.4 当前阶段的正确判断

到 `v21` 为止，可以把这段经验总结成一句话：

> `intro + /audio` 并行的关键，不是“尽快把流开起来”，而是“让后台流在 intro 期间先收先缓存，但不要错误地把它当成已经进入应该整条收完的主播放阶段”。

换句话说：

- 并行的是收流
- 不是抢播
- 也不是“intro 一结束就要求后台流马上整条结束”

### 27.5 下一轮联调时最该盯的点

1. `stage=intro_and_audio_parallel event=wait_timeout` 是否消失
