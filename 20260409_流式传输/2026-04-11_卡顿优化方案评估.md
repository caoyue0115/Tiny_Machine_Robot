# 2026-04-11 卡顿优化方案评估

## 1. 基线（来自 bug15）

- `first_audio_byte_local_ms ≈ 7128ms`
- `stream_audio elapsed ≈ 14961ms`
- `total_stream_bytes = 307200`
- 按 `16k/16bit/mono` 折算实际音频时长：`307200 / 32000 = 9.6s`
- `VAD` 已生效：
  - `Captured 88064 bytes in 2.743s`
  - `vad_stopped=1`
  - 固定 `4s` 录音等待已经被压缩
- bug15 中 `first_audio_byte_local_ms ≈ 7128ms` 是从触摸开始算的端到端首包时间，不是纯云端首包时间
- 可拆解为：
  - 录音约 `2.8s`
  - `POST /sessions` 约 `1.3s`
  - `/audio` 建连到首包约 `2.9s`
- 当前更准确结论：
  - `stream_audio` 总耗时大于音频时长，说明播放过程中存在供给空档或板端等待
  - 但原日志没有 `underrun_count`、`underrun_ms`、真实 `playback_start`、chunk 间隔统计
  - 因此不能直接断言“平均生产速度 < 播放速度”，需要先补细粒度日志定位

## 1.1 已决定的诊断增强

先不继续盲调 buffer / pacing，优先补日志：

- HTTP 拉流侧：
  - `chunk_count`
  - `first_chunk_bytes`
  - `last_chunk_bytes`
  - `max_inter_chunk_gap_ms`
  - `avg_inter_chunk_gap_ms`
- jitter 播放侧：
  - `playback_actual_start_ms`
  - `prebuffer_wait_ms`
  - `underrun_count`
  - `underrun_ms`
  - `min_level`
  - `max_level`
- 新增 summary 日志：

```text
realtime_audio_summary session_id=... total_bytes=... chunk_count=... max_gap_ms=... avg_gap_ms=... prebuffer_wait_ms=... playback_actual_start_ms=... underrun_count=... underrun_ms=... min_level=... max_level=... total_in=... total_out=...
```

下一轮 bug 日志优先用这行判断：

- `underrun_count > 0` 且 `max_gap_ms` 高：优先考虑服务端 pacing / 句间静音填隙
- `underrun_count > 0` 但 `max_gap_ms` 不高：优先查板端播放任务或 codec 写阻塞
- `underrun_count = 0` 但仍主观断续：优先查 TTS 段间声学不连续、拼接边界或 codec 侧问题

## 2. 六项方案综合评估

### 2.1 加强预缓冲

- 目标：降低欠载和断续
- 预期效果：稳定性提升明显
- 时间影响：通常不节约，总时长可能不变；首播通常增加 `0.2s ~ 1.0s`
- 风险：参数过大时交互变“迟钝”
- 结论：建议做动态预缓冲，不建议固定拉满

### 2.2 首字前固定加 2 秒出场声

- 目标：降低“等待焦虑”，改善感知卡顿
- 预期效果：主观体验明显改善
- 时间影响：串行方案会增加总时长约 `+2.0s`
- 风险：固定 2 秒容易显得模板化、拖沓
- 结论：可做，但建议可配置且可跳过

2026-04-11 实施记录：

- 先落地 `1.5s` 左右的板端本地开场声，不走云端生成
- 开场声资源转为 `16kHz/16-bit/mono/little-endian` 裸 PCM，约 `48KB`
- 因 app 分区空间不足，已同步扩容分区并新增 SPIFFS：
  - app `factory`: `2MB`
  - SPIFFS `storage`: `4MB`
- 第一版采用串行播放：`post_session -> intro -> open_audio -> stream_audio`
- 开场声失败不阻塞主链路，仅记录 `realtime_intro_failed`
- 后续如果要继续压真实等待，可评估“开场声播放与 /audio 建连并行”

### 2.3 音频自然放慢到 0.8x

- 目标：提升清晰度和“听感从容度”
- 预期效果：可懂度可能提高
- 时间影响：音频时长约 `+25%`
- 风险：显著拉长播放，放大卡顿感知
- 结论：**慢速方案当前不考虑实施，仅记录**

### 2.4 回答长度限制到 25 字

- 目标：从源头减少生成和播放负担
- 预期效果：时延和卡顿同步改善
- 时间影响：预计节约 `2.5s ~ 5.0s`（随原回答长度变化）
- 风险：信息量下降
- 结论：优先级高，建议先实施

### 2.5 换更快的 flash 模型

- 目标：降低首字可用时间，缩短上游空档
- 预期效果：首包更快，整体可能更稳
- 时间影响：预计首字 `-0.5s ~ -1.5s`，总时长 `-0.5s ~ -2.5s`
- 风险：回答质量、术语准确性可能回退
- 结论：已实施，仍需实板验证主观质量

2026-04-11 实施记录：

- `LLM_MODEL` 已从 `qwen-max-latest` 改为 `qwen3.5-flash-2026-02-23`
- LLM 调用已增加 `extra_body={"enable_thinking": False}`
- 远端已同步并重建 API/worker，`/healthz` 全 `ok`
- `immediate` smoke 两轮：
  - `first_audio_byte_ms=2726 / 2130`
  - `first_llm_chunk_ms=2368 / 1703`
  - trace `production_ratio=3.907 / 3.812`
  - `audio_max_chunk_gap_ms=134 / 144`
  - `virtual_player.underrun_count=0`
- 结论：云端生产速度已经明显快于播放速度，卡顿排查重心转向实板 underrun、TTS 拼接边界和 codec 播放侧

### 2.6 逗号/自然停顿处加少量静音帧

- 目标：把“机械卡顿感”转为“自然停顿”
- 预期效果：听感改善
- 时间影响：小幅增加，总计约 `+0.2s ~ +0.8s`（取决于停顿次数）
- 风险：插入过多会变成人为卡顿
- 结论：可作为后置润色项，小剂量启用

## 3. 综合优先级

按“稳定 + 体验 + 风险”综合排序：

1. `方案4` 回答限制 25 字
2. `方案5` 更快 flash 模型（已实施，需实板质量回归）
3. `方案1` 动态预缓冲
4. `方案2` 可配置出场声（第一版已实现为板端 SPIFFS 开场声）
5. `方案6` 标点小剂量静音
6. `方案3` 慢速（仅记录，不纳入当前实施）

## 4. 当前决策（本次评审）

- 慢速播放（`0.8x`）作为“记录项”，不进入当前默认链路
- 当前已实施：`5`、`2`、基础 `1`
- 下一步主线：实板复测 `realtime_audio_summary`，再决定是否做回答长度限制或 TTS 拼接/填隙
- `2` 与 `6` 作为体验层增强，在主线稳定后再进入
