## 3. v3 接口

### 3.1 创建 session

- `POST /api/v3/realtime/sessions`
- 请求头：
  - `Content-Type: application/octet-stream`
  - `x-device-id`
  - `x-sample-rate: 16000`
  - `x-sample-width: 16`
  - `x-channels: 1`
- 请求体：
  - 原始 `PCM`
  - `16kHz / 16-bit / mono / little-endian`

### 3.2 查状态

- `GET /api/v3/realtime/sessions/{session_id}`
- 重点看：
  - `status`
  - `step`
  - `final_reason`
  - `trace`
  - `error_code`
  - `error_message`

### 3.3 拉音频

- `GET /api/v3/realtime/sessions/{session_id}/audio`
- 返回：
  - `HTTP chunked`
  - `Content-Type: application/octet-stream`
  - 裸 `PCM`

响应头固定值：

- `X-Audio-Sample-Rate: 16000`
- `X-Audio-Sample-Width: 16`
- `X-Audio-Channels: 1`
- `X-Audio-Endian: little`

## 6. 常见失败与优先排查

- `audio_consumer_exists`
  - 同一 `session` 有第二个消费者接入
- `stream_first_chunk_timeout`
  - 服务端超过首包超时仍未产出音频
- `stream_idle_timeout`
  - 音频流中途长时间无新 chunk
- `llm_request_failed`
  - 先看云端 `worker` 日志
- `tts_*`
  - 先看 `REALTIME_TTS_VOICE` 和 provider 日志

## 7. 板端侧最先该看的问题

如果服务端 trace 正常，但板端仍慢很多，优先看：

- chunk 接收是不是整包等满才往下交
- ring buffer 是否过大
- 播放线程是否在首包后仍等待额外缓冲
- HTTP 读取线程和播放线程是否串行阻塞

## 8. bug13：返包说话断断续续

现象：

- `/audio` 能成功拉流
- `pipeline result=ok`
- 但喇叭播放听起来断断续续

原因判断：

- 服务端当前仍可能按“首段音频 -> 等下一段 -> 再出音频”的节奏下发 `PCM`
- 板端如果收到 chunk 就直接写 codec，会把云端段间空档直接听成断续
- Wi-Fi 省电会进一步放大包到达抖动

当前板端处理：

- `DEMO_WIFI_POWER_SAVE_NONE=1`，联调默认关闭 Wi-Fi 省电
- `audio_out_write_pcm_chunk_buffered()` 增加轻量 jitter buffer
- HTTP 读取回调只入队，播放任务按固定小块写 codec
- 默认预缓冲：
  - `DEMO_REALTIME_AUDIO_JITTER_BUFFER_BYTES=65536`
  - `DEMO_REALTIME_AUDIO_JITTER_PREBUFFER_BYTES=40960`
  - `DEMO_REALTIME_AUDIO_JITTER_READ_BYTES=1024`

如果仍断续，下一步优先看串口里的：

- `realtime_audio_summary ...`
- `Realtime jitter playback task done total_in=... total_out=... min_level=... max_level=... underrun_count=... underrun_ms=... prebuffer_wait_ms=...`
- `total_stream_bytes`
- `stage=stream_audio elapsed_ms`

判断规则：

- `underrun_count > 0` 且 `max_gap_ms` 高：优先考虑服务端 pacing / 句间静音填隙
- `underrun_count > 0` 但 `max_gap_ms` 不高：优先查板端播放任务或 codec 写阻塞
- `underrun_count = 0` 但仍主观断续：优先查 TTS 段间声学不连续、拼接边界或 codec 侧问题

## 11. bug16：多轮后触摸无反应

硬件同事反馈的 `esp_idf_demo_handoff_2026-04-11_v4.tar.gz` 属于分区扩容和开场声之前的版本，只增加了更细粒度日志。`bug16.txt` 当前只有一次 `USB_UART_CHIP_RESET` 后的启动日志，没有包含触摸、pipeline 或播放关闭阶段日志，因此不能直接从日志证明最终卡在哪个函数。

代码侧发现两个高风险点，已按最小改动修复：

- 主循环原来只有在 `APP_STATE_IDLE && s_pipeline_task_handle == NULL` 时才调用 `trigger_input_poll`。如果上一轮还没完全结束或卡在清理阶段，后续触摸不会被轮询，也不会有任何日志。现在改为每轮都先轮询触摸，忙时打印 `Trigger ignored: source=... state=... pipeline_task=...`。
- jitter 播放关闭原来用 `eTaskGetState(stream_task) != eDeleted` 等待播放任务删除。任务已经 `vTaskDelete(NULL)` 后，外部继续查询旧 task handle 存在不可预测风险。现在改为播放任务退出前设置显式 `stream_task_done` 标志，close 只等待该标志。

复测时如果再次出现“点屏幕没反应”，需要从第一次点击开始持续抓串口，重点看：

- 是否出现 `Trigger ignored`
- 忙时的 `state` 是什么
- `pipeline task finished` 是否出现
- `Realtime jitter playback task done ...` 是否出现
- 如果没有 `pipeline task finished`，优先看最后一个 `stage=...` 停在录音、网络、stream_audio 还是 close 阶段

## 12. bug18：流结束后没有任务结束，触摸无效

`bug18_1.txt` 和 `bug18_2.txt` 来自 v6，即还没有合入 bug16 两个任务生命周期防护的版本。日志显示两个事实：

- 卡顿确实存在：多轮 `realtime_audio_summary` 都有较高 `underrun_count` 和 `underrun_ms`，例如 `underrun_count=1253 underrun_ms=24759.1`，说明当时上游 chunk 供给不均，播放端发生欠载。
- “触摸无效”是另一个问题：`bug18_2` 最后一轮已经打印 `stage=stream_audio event=done` 和流统计，但没有 `Realtime jitter playback task done`、没有 `realtime_audio_summary`、没有 `pipeline task finished`，说明卡在 stream 结束后的 jitter 播放任务收尾/close 阶段，主状态没有回到 idle。

具体根因：

- jitter 播放任务内部使用 `scratch[DEMO_REALTIME_AUDIO_JITTER_READ_BYTES]` 聚合写 codec。
- 旧逻辑只有 `scratch_len == 0` 才允许退出。
- 如果最后一个 PCM chunk 不是 `1024` 字节对齐，例如 `bug18_2` 最后一轮 `last_chunk_bytes=1536`，任务会写出其中 `1024` 字节，剩余 `512` 字节留在 `scratch_len`。
- 流已经结束后不会再有新 ringbuffer item，旧逻辑既不会 flush 这段尾包，也不会退出，于是 close 等不到播放任务完成，pipeline 不会回 idle，触摸看起来无效。

修复方式：

- 当 `stream_task_started=false` 且 ringbuffer 水位为 `0` 时允许播放任务退出。
- 退出循环后复用已有 `if (scratch_len > 0)` 逻辑 flush 尾包。
- 结合 bug16 修复，close 等待 `stream_task_done` 显式标志，而不是查询已删除 task handle。

复测判断：

- 每一轮都应该出现 `Realtime jitter playback task done`
- 每一轮都应该出现 `realtime_audio_summary`
- 每一轮最终都应该出现 `pipeline task finished`
- 如果还有卡顿，再看 `underrun_count`、`max_gap_ms`、`avg_gap_ms`，那属于上游供给/播放欠载问题，不应再导致触摸永久无效

## 13. 2026-04-12 回答长度与预缓冲调整

本轮先做两项低风险体验优化，暂不做“开场声与 `/audio` 并行”：

- 服务端 LLM prompt 增加“总回答约 `25` 到 `35` 字”，保留“首句 `6` 到 `10` 个字直接回答”
- 板端 jitter buffer 默认从 `32768B` 提到 `65536B`
- 板端 jitter prebuffer 默认从 `24576B` 提到 `40960B`

换算依据：

- `16kHz / 16-bit / mono` 等于 `32000B/s`
- 额外 `0.5s` 约等于 `16000B`
- 旧 prebuffer `24576B` 加 `16000B` 后按 `1024B` 对齐取 `40960B`
- buffer 取 `65536B`，避免 prebuffer 逼近总容量

复测重点：

- `prebuffer_wait_ms` 预计增加约 `500ms`
- 如果上游供给仍明显不均，`underrun_count` 应下降但不一定归零
- 如果回答长度控制生效，`total_stream_bytes` 和 `chunk_count` 应下降
- 如果仍觉得等待长，再考虑“开场声播放期间提前连接 `/audio` 并预取到 jitter buffer”
