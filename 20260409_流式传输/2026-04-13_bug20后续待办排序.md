# bug20 后续待办排序

日期：2026-04-13

背景：本文件合并两轮建议：

- 上一轮：基于小智 `xiaozhi-esp32` 借鉴后的技术排序。
- 这一轮：基于 `bug20.txt` 新网络日志和云端 session trace 的修正排序。

目标：避免把网络、播放、录音、唤醒、Opus 多个变量混在一起改，先建立可观测闭环，再逐步收敛卡顿和交互问题。

## 0. 当前状态补充

本排序文档基于 `bug20` 写成，之后实现状态已有变化，先补充当前事实：

- 板端**已加入轻量能量 VAD**，现在是“最长 `4s` + VAD 提前结束”，不是纯固定录满 `4s`。
- 但“唤醒后等待用户开口、无语音不上传、检测说完后结束”的**完整动态等待状态机仍未实现**，所以 `P4` 仍然成立。
- `stream_audio done` 后的收尾已经加了**超时保护**，不会再无限挂住；但在高反压场景里仍可能以 close timeout 失败结束，所以 `P2` 仍未算完全关闭。
- 当前 `audio_format` 已支持 `opus/pcm` 协商，且云端可开启 Opus；但仍需最新实机日志确认是否真正跑到 `audio_format=opus`。
- 当前**没有**“同一会话中自动从 `v3` 静默 fallback 到 `v2`”的逻辑；`v2/v3` 仍应按会话开始前策略选择。

## 1. bug20 关键结论

### 1.1 云端不是这次主因

`bug20.txt` 的 session：

```text
session_id=f6eaaa42-85ec-4002-8a06-1a85bd6cc190
question_text=什么是金刚经？
```

板端日志：

```text
first_audio_byte_local_ms=5275.2
stream_audio elapsed_ms=18199.9
total_stream_bytes=289280
chunk_count=71
max_inter_chunk_gap_ms=3514.2
avg_inter_chunk_gap_ms=232.0
```

音频长度换算：

```text
289280 bytes / 16000Hz / 2 bytes = 9.04 秒音频
```

也就是说：

```text
9.04 秒音频，板端流式接收用了 18.2 秒
```

云端同 session trace：

```json
{
  "asr_ms": 960,
  "first_llm_chunk_ms": 1744,
  "first_tts_chunk_ms": 2116,
  "first_audio_byte_ms": 2116,
  "done_ms": 4498,
  "audio_bytes": 289280,
  "audio_duration_ms": 9040,
  "audio_stream_wall_ms": 2317,
  "audio_max_chunk_gap_ms": 141,
  "production_ratio": 3.902
}
```

判断：云端 4.5 秒完成整个 session，音频流 wall 2.317 秒，最大 chunk gap 141ms，生产速度足够快。因此这次卡顿不能优先归因于云端生成慢或香港服务器节点慢。

### 1.2 板端或链路侧仍存在长尾

板端看到：

```text
max_inter_chunk_gap_ms=3514.2
```

但这个 gap 不能直接等价为纯网络 gap。它可能来自：

- 真实 Wi-Fi/TCP 抖动。
- HTTP read 被 callback 阻塞。
- jitter ringbuffer 满导致 enqueue 卡住。
- I2S/codec 写入慢导致下游消费慢。
- 播放任务没有及时退出，导致 close 卡住。

当前 `bug20.txt` 没有 `max_enqueue_ms`、`avg_enqueue_ms`、`Realtime jitter close waiting`、`realtime_audio_summary`，所以还不能分清是网络长尾还是播放反压。

### 1.3 SPIFFS 仍未刷入

日志：

```text
SPIFFS mounted: label=storage total=3848081 used=0
Failed to open PCM file: /spiffs/intro_1.pcm
realtime_intro_failed err=ESP_FAIL
```

判断：仓库资源不是缺失，板端 SPIFFS 为空。需要正确刷 `storage.bin`。

### 1.4 播放结束收尾仍未回 idle

日志里有：

```text
stage=stream_audio event=done elapsed_ms=18199.9
Trigger ignored: source=touch state=streaming_audio pipeline_task=busy
```

但没有看到：

```text
Realtime jitter playback task done ...
realtime_audio_summary ...
pipeline result=ok ...
State transition: ... -> idle
```

判断：`stream_audio done` 后 pipeline 没有正常完成，状态仍停在 `streaming_audio`，所以后续触摸被忽略。这和 `bug19` 的“触屏警告”是同类现象：触摸 warning 是结果，不是根因。

`bug20` 后，技术排序需要临时前移诊断和收尾修复。


## 3. P0：刷最新诊断固件 + SPIFFS

### 3.1 目的

先保证后续日志足够判断根因。不然每次只能看到 `max_inter_chunk_gap_ms`，无法知道它来自网络还是板端反压。

### 3.2 必须看到的新日志字段

新版固件应输出：

```text
max_enqueue_ms
avg_enqueue_ms
Realtime jitter close waiting ...
Realtime jitter playback task done ...
realtime_audio_summary ...
```

如果日志里没有这些字段，说明板端不是最新诊断固件。

### 3.3 SPIFFS 验收

当前失败状态：

```text
SPIFFS mounted ... used=0
Failed to open PCM file: /spiffs/intro_1.pcm
```

修复后应该看到：

```text
SPIFFS mounted ... used>0
```

并且不再出现：

```text
Failed to open PCM file: /spiffs/intro_1.pcm
```

注意：开场音资源仓库里有，主要风险是 `storage.bin` 没刷或刷错地址。

## 4. P1：复测并采集完整指标

### 4.1 每次复测需要保留的信息

板端日志至少保留：

```text
session_id=...
first_audio_byte_local_ms=...
stream_audio event=done elapsed_ms=...
total_stream_bytes=...
chunk_count=...
max_inter_chunk_gap_ms=...
avg_inter_chunk_gap_ms=...
max_enqueue_ms=...
avg_enqueue_ms=...
Realtime jitter close waiting ...
Realtime jitter playback task done ...
realtime_audio_summary ...
pipeline result=...
State transition: ... -> idle
Trigger ignored ...
```

云端需要用 `session_id` 对应 trace：

```text
asr_ms
first_llm_chunk_ms
first_tts_chunk_ms
first_audio_byte_ms
done_ms
audio_stream_wall_ms
audio_max_chunk_gap_ms
production_ratio
```

网络需要记录：

```text
ping_loss
http_avg_ms
http_max_ms
http_jitter_ms
```

### 4.2 如何判断问题归因

| 现象 | 更可能原因 |
| --- | --- |
| 云端 `audio_max_chunk_gap_ms` 大，板端也大 | 云端生成/服务端流式长尾 |
| 云端 gap 小，板端 gap 大，`max_enqueue_ms` 小 | Wi-Fi/TCP/板端 HTTP read 长尾 |
| 云端 gap 小，板端 gap 大，`max_enqueue_ms` 大 | callback 写入 jitter 阻塞或 ringbuffer 反压 |
| `total_in > total_out` 长时间不变 | 播放任务消费慢或卡住 |
| `total_in == total_out` 但 close 不退出 | stream task exit 条件/状态同步问题 |
| `underrun_count > 0` 且 gap 大 | 网络/生成速度低于播放速度 |
| `underrun_count = 0` 但状态不回 idle | 收尾 close/task done 问题 |

## 5. P2：修播放收尾不能回 idle

### 5.1 当前症状

`bug20` 中：

```text
stage=stream_audio event=done
```

之后没有：

```text
realtime_audio_summary
pipeline result=ok
State transition: ... -> idle
```

后续触摸：

```text
Trigger ignored: source=touch state=streaming_audio pipeline_task=busy
```

### 5.2 技术目标

无论音频是否卡顿，流式播放结束后必须满足：

```text
stream_audio done
-> close jitter stream
-> playback task exits
-> realtime_audio_summary printed
-> pipeline result printed
-> state returns idle
-> next touch accepted
```

### 5.3 验收标准

每次播放结束必须看到：

```text
Realtime jitter playback task done ...
realtime_audio_summary ... total_in=... total_out=...
pipeline result=ok ...
State transition: done -> idle
```

并且下一次触摸不应被：

```text
pipeline_task=busy
```

拦截。

## 6. P3：判断是否需要 buffer、回调策略或 Opus

在 P1/P2 完成前，不建议直接调大 buffer 或改 Opus。原因是 `max_inter_chunk_gap_ms=3514.2` 还没有被归因。

### 6.1 如果是 Wi-Fi/TCP 抖动

可选动作：

- 增大 jitter prebuffer。
- 增大 jitter ringbuffer。
- 做 v3 下行 Opus。
- 差网络下会话前选择 `v2_preload`。

### 6.2 如果是 callback/enqueue 阻塞

可选动作：

- HTTP receive 与 audio enqueue 再解耦。
- callback 只入轻量网络队列，不直接写播放 ringbuffer。
- 播放 ringbuffer 满时记录 drop/block 策略，不能无界阻塞 HTTP read。

### 6.3 如果是播放 task close 卡住

可选动作：

- 修 stream task exit 条件。
- close 时增加超时和强制终止保护。
- close 日志持续打印 `total_in/total_out/level/playback_started/underrun_count`。

## 7. P4：动态等待 / VAD 录音结束

### 7.1 技术判断

完整动态等待状态机应排在 Opus 前面，但排在当前诊断和收尾修复之后。

原因：虽然当前已经有“最长 4 秒 + 轻量 VAD 提前结束”，但交互层面仍缺少等待用户开口的状态机，会导致：

- 用户还没说就上传空音频。
- 用户没说完就截断。
- 唤醒后体验不自然。

### 7.2 推荐状态机

```text
Idle
  -> WakeOrTouch
  -> Prompting
  -> ListeningPending
  -> ListeningSpeech
  -> ListeningEnding
  -> Uploading
  -> StreamingAudio or PreloadAudio
  -> Idle
```

### 7.3 初版参数

```text
wait_speech_start_ms = 6000-8000
min_speech_ms = 500-700
end_silence_ms = 800-1200
max_utterance_ms = 10000-12000
```

### 7.4 无语音策略

不再上传保底 4 秒空音频。

建议：

```text
第一次无语音 -> 本地提示“我在听，请再说一遍。”
第二次无语音 -> 回到 Idle
```

## 8. P5：开场音与 /audio 并行

### 8.1 推荐流程

```text
session accepted
  -> start local prompt playback
  -> immediately start /audio request in background
  -> cloud audio arrives: only enqueue/cache, not play over prompt
  -> local prompt done
  -> start cloud jitter prebuffer
  -> play cloud audio
```

### 8.2 关键约束

- 本地 prompt 不应阻塞 `/audio` 请求。
- 云端音频不能和本地 prompt 混播。
- prompt 建议控制在 0.8-1.5 秒。
- 如果云端音频先到，只缓存，等本地提示结束再播。

### 8.3 前置条件

必须先解决：

- SPIFFS 正确刷入。
- 播放收尾能回 idle。
- 状态机清晰，不会出现两个播放任务互相抢 codec。

## 9. P6：v3 下行 Opus

### 9.1 推荐范围

第一版只做下行 Opus：

```text
server TTS PCM
-> server encode Opus
-> HTTP chunked /audio returns Opus frames
-> board decodes Opus
-> PCM jitter queue
-> I2S playback
```

暂时不要同时做上行 Opus。

### 9.2 原因

- 当前主要卡顿在语音返回，下行收益最大。
- 上行录音只有几秒，带宽压力较小。
- 同时改上下行会增加定位难度。

### 9.3 必须保留 fallback

必须保留：

```text
audio_format=pcm
```

否则 Opus decoder、帧边界、采样率协商、PSRAM 任一环出问题都会影响演示。

### 9.4 建议帧格式

先不要直接裸 Opus 拼流，建议简单长度前缀：

```text
uint16_be payload_len + opus_payload
uint16_be payload_len + opus_payload
...
```

响应头：

```http
X-Audio-Format: opus
X-Opus-Sample-Rate: 24000
X-Opus-Channels: 1
X-Opus-Frame-Duration-Ms: 60
```

### 9.5 验收指标

```text
opus_bytes / pcm_bytes <= 0.2
decode_fail_count = 0
decode_max_ms < frame_duration_ms * 0.3
underrun_count 比 PCM 明显下降
PCM fallback 可用
```

## 10. P7：v2/v3 会话前链路选择

### 10.1 原则

不要做一次会话中静默 fallback。

建议会话开始前选择：

```text
网络好 -> v3_stream
网络差 -> v2_preload
固定讲解/必须完整播完 -> v2_preload
```

### 10.2 选择依据

| 条件 | 建议链路 |
| --- | --- |
| 最近 3 次 v3 `underrun_count=0` 且 `max_gap_ms < 500` | v3_stream |
| HTTP healthz 长尾 > 800ms | v2_preload |
| 最近一次板端 `max_gap_ms > 1000` | v2_preload |
| 最近一次板端 `underrun_count > 0` | v2_preload |
| 会展现场 2.4G 明显拥塞 | v2_preload |
| 固定讲解/必须完整播完 | v2_preload |

### 10.3 日志要求

每次会话打印：

```text
selected_path=v3_stream|v2_preload
selected_reason=...
network_score=...
last_max_gap_ms=...
last_underrun_count=...
```

## 11. P8：提示词/唤醒词接入

### 11.1 排在后面的原因

提示词/唤醒词不应早于状态机稳定。

原因：

- 它只是新的触发源，不能修复播放卡顿。
- 如果状态机不稳，唤醒词只会更频繁触发 busy/卡死。
- 真正 ESP-SR 唤醒词还涉及模型、分区、PSRAM、AEC/VAD 参数。

### 11.2 推荐拆分

```text
阶段 A：触摸/按钮先接入动态等待状态机
阶段 B：提示词唤醒只作为新的 trigger source
阶段 C：再评估 ESP-SR 自定义唤醒词
```

### 11.3 唤醒词音频缓存

后续如果做真正唤醒词，建议保留唤醒前后 1-2 秒音频缓存，避免用户说完唤醒词后前几个问题字被丢失。

## 12. P9：长期架构项

这些不建议进入当前会展稳定化主线：

- 上行 Opus。
- WebSocket 全链路迁移。
- MQTT 控制 + UDP 加密音频。
- 完整迁移小智 C++ Application/Board/Protocol 框架。
- 设备侧 MCP/display 高级功能。

可以作为产品化方向，但当前会展版本优先级低于稳定播放和动态等待。

## 14. 当前一句话结论

先不要急着做 Opus 或唤醒词。`bug20` 显示云端生成正常，但板端流式接收/播放/收尾还有未归因问题；下一步必须先刷最新诊断固件和 SPIFFS，复测拿到 `max_enqueue_ms`、`realtime_audio_summary`、close wait 日志，再决定是修播放反压、Wi-Fi 抖动，还是进入 Opus。
