# 首字延迟优化方案

日期：`2026-04-17` 

## 1. 文档目的

本文档面向开发工程师，聚焦 `20260409_流式传输` 这条并行探索线里的“首字延迟”优化，不重复介绍整套 `v3/realtime` 架构。

本文回答四个问题：

- 首字延迟在本项目里如何定义与拆账
- 当前链路的主要瓶颈已经转移到哪里
- 哪些优化项已经验证有效，哪些还应继续推进
- 后续应按什么顺序实施，如何验收

## 2. 术语与口径

### 2.1 首字延迟定义

本项目里的“首字延迟”，建议统一用两个口径同时看：

1. 云端首字延迟  
   从服务端收到 `POST /api/v3/realtime/sessions` 开始，到 `/audio` 首个音频字节可被下游读取为止。  
   主要看 `trace.first_audio_byte_ms`。

2. 端到端首字延迟  
   从板端触发开始，到板端实际听到第一段语音为止。  
   这个指标会额外包含录音、上传建连、板端预缓冲和 codec 播放启动。

两者不能混用。  
`云端快` 不代表 `端到端快`，因为板端仍然可能被录音时长、Wi-Fi 长尾、预缓冲策略拖慢。

### 2.2 分段指标

建议把首字延迟固定拆成以下几段：

- 录音段：板端触发到录音结束
- 上传段：录音结束到 `POST /sessions` 返回
- ASR 段：`trace.asr_ms`
- 检索段：`trace.retrieval_ms`
- LLM 首段：`trace.first_llm_chunk_ms`
- TTS 首段：`trace.first_tts_chunk_ms`
- 云端首包：`trace.first_audio_byte_ms`
- 板端起播：`first_audio_byte_local_ms` / `playback_actual_start_ms`

其中真正和“更早出声”最相关的，不是总耗时，而是：

- `trace.first_audio_byte_ms`
- `first_audio_byte_local_ms`
- `prebuffer_wait_ms`

在 `intro + /audio` 并行已接入之后，还应补看两个更干净的端侧指标：

- `intro_end_to_first_audio_byte_ms`
- `open_audio_to_first_audio_byte_ms`

原因：

- `first_audio_byte_local_ms` 会混入提示音、等待开口、重讲重等、录音时长等前段耗时
- 这两个新指标更适合单独评估“并行 intro 是否真正让用户更早听到云端首音”

## 3. 当前现状判断

### 3.1 已验证的阶段性结论

基于 `2026-04-10` 到 `2026-04-13` 的 smoke、trace 和板端日志，当前已经可以确认：

- `LLM stream=True` 已生效，`LLM` 不再是首字延迟的首要瓶颈
- realtime TTS 已接入主链路，`first_tts_chunk_ms` 已从约 `8.4s` 压到约 `5.5s`，再压到约 `3.3s`
- 进一步切换 `qwen3.5-flash-2026-02-23` 并关闭 `thinking` 后，云端 `first_audio_byte_ms` 已稳定进入约 `2.1s ~ 2.7s`
- `production_ratio` 已达到约 `3.8 ~ 3.9`，说明云端产流速度明显高于播放速度
- 脚本虚拟播放器 `virtual_player.underrun_count=0`，说明在 PC 拉流视角下，云端连续供给已基本不是主要问题

这意味着当前优化重心已经发生变化：

- 第一阶段瓶颈：`LLM` 首段慢
- 第二阶段瓶颈：`TTS` 首段慢
- 当前阶段瓶颈：端到端录音前置耗时、板端预缓冲、弱网长尾、板端播放侧抖动

### 3.2 当前可参考的实测区间

当前文档与日志里已有的代表性数字如下：

- 较早阶段：
  - `first_llm_chunk_ms: 4563 -> 2316`
  - `first_tts_chunk_ms: 9010 -> 8389`
- 接入 realtime TTS 后：
  - `first_llm_chunk_ms: 2285`
  - `first_tts_chunk_ms: 5469`
  - `first_audio_byte_ms: 5469`
- 启用轻预热 + retrieval 瘦身后：
  - `asr_ms=1096`
  - `retrieval_ms=628`
  - `first_llm_chunk_ms=2642`
  - `first_tts_chunk_ms=3314`
  - `first_audio_byte_ms=3314`
- 切换 flash 模型并关闭 thinking 后：
  - `first_audio_byte_ms=2726 / 2130`
  - `first_llm_chunk_ms=2368 / 1703`
  - `production_ratio=3.907 / 3.812`
  - `audio_max_chunk_gap_ms=134 / 144`
  - `virtual_player.underrun_count=0`

结论很明确：  
云端首包优化已经取得明显收益，后续收益最大的空间不在“继续盲目压 LLM token 首段”，而在“减少录音等待 + 缩短板端起播前等待 + 提升弱网稳定性”。

### 3.3 2026-04-16 网络实测补充结论（新增）

基于 Windows 现场网络测试（同一公网服务器）：

- 测试一：`ping` 丢包约 `20%`，`HTTP avg=334.3ms`，`jitter=1881.4ms`
- 测试二（手机热点复测）：`ping` 丢包约 `23%`，`HTTP avg=235.1ms`，`jitter=1117.5ms`

结论：

- 这类网络条件下，“返包断续/中途停顿”会显著放大
- 即使云端 `first_audio_byte_ms` 已优化到 `2.xs`，端侧仍可能出现“10秒音频播放拉长到20秒+”的体感问题
- 因此当前阶段必须把“网络质量基线”作为与代码同优先级的排障入口，不能只从算法或参数侧解释所有卡顿

### 3.4 2026-04-17 首字观测口径更新（新增）

基于 `bug44 ~ bug47` 的现场日志，可以确认：

- `intro + /audio` 并行收流已经上线，且 `wait_timeout` 误判已修正
- 新增的：
  - `intro_end_to_first_audio_byte_ms`
  - `open_audio_to_first_audio_byte_ms`
  已经能够稳定出数
- 现场代表性区间大致在：
  - `intro_end_to_first_audio_byte_ms ≈ 0.7s ~ 1.5s`
  - `open_audio_to_first_audio_byte_ms ≈ 0.6s ~ 1.5s`

这说明当前并行 `intro` 不是“没生效”，而是：

- 真正的收益已经能从新指标里看到
- 但旧指标 `first_audio_byte_local_ms` 仍会因为 `waiting_speech`、重试提示音、录音预算等前段环节被显著放大

因此后续若要判断“并行 intro 有没有价值”，**不要再只看 `first_audio_byte_local_ms`**。

## 4. 首字延迟瓶颈拆解

### 4.1 板端录音前置耗时

当前输入侧仍是“先整段录音，再上传”，所以端到端首字延迟天然受录音时长影响。

即使云端 `first_audio_byte_ms` 已经做到约 `2.1s ~ 2.7s`，只要板端仍先录 `2s ~ 4s`，端到端首字延迟就不可能接近云端数字。

当前已实施的正确方向：

- 引入 `VAD`
- 允许在达到最小时长后提早截断录音

当前判断：

- 这是端到端首字延迟的一级大头
- 但它不属于云端 `TTFT` 问题，而是输入侧产品形态问题
- 在不做边录边传之前，只能靠更稳的 `VAD` 和更短的最小录音时长继续压缩

### 4.2 TTS 首段准备耗时

历史数据表明，`TTS` 一度是最大的云端首字瓶颈。当前已实施的有效措施包括：

- 使用 realtime 专用 `voice_id`
- 轻预热 realtime TTS session
- 更激进的首段切片阈值
- 让 LLM 先输出更短的首句

当前判断：

- `TTS` 仍是云端链路中最值得关注的一段
- 但它已经从“阻断性瓶颈”变成“可控瓶颈”
- 后续优化要避免收益递减下的复杂度膨胀

### 4.3 板端预缓冲与起播策略

当前板端采用 jitter buffer + prebuffer 的方式保障连续播放。  
这对抗弱网和 chunk 抖动是必要的，但也会直接抬高首播时间。

已知现状：

- `DEMO_REALTIME_AUDIO_JITTER_BUFFER_BYTES` 已增大到 `65536`
- `DEMO_REALTIME_AUDIO_JITTER_PREBUFFER_BYTES` 已增大到 `40960`
- 已补充 `underrun_count`、`underrun_ms`、`prebuffer_wait_ms`、`min_level`、`max_level` 等日志

当前判断：

- 这是当前最需要精调的端侧参数区
- 预缓冲偏小会卡顿，偏大则会牺牲首字
- 应以实测日志驱动，而不是继续经验调参

### 4.4 网络长尾与板端播放侧抖动

当前 PC smoke 已显示云端 chunk 供给较稳，但板端现场仍可能受到以下因素影响：

- `2.4GHz Wi-Fi` 干扰
- 手机热点中继
- 板端任务调度抖动
- codec 写阻塞

因此，必须区分两类问题：

- 云端首包慢
- 云端已经够快，但板端仍晚起播或中途断续

判断规则建议保持如下：

- 若 `underrun_count > 0` 且 `max_gap_ms` 高：优先看网络和服务端供给间隙
- 若 `underrun_count > 0` 但 `max_gap_ms` 不高：优先看板端播放任务或 codec
- 若 `underrun_count = 0` 但主观仍断续：优先看 TTS 拼接边界、声学不连续或板端播放细节

## 5. 已验证有效的优化项

下表只列“已经有数据支持”的项。

| 优化项 | 当前状态 | 主要收益 | 备注 |
| --- | --- | --- | --- |
| `LLM stream=True` | 已上线 | 提前得到首段文本 | 已不是主瓶颈 |
| 切换 `qwen3.5-flash-2026-02-23` | 已上线 | 压低 `first_llm_chunk_ms` | 需持续关注回答质量 |
| `enable_thinking=False` | 已上线 | 去掉 thinking 额外等待 | 收益明确，建议保持 |
| realtime 专用 `voice_id` | 已上线 | 让 realtime TTS 真正可用 | 是前置条件，不是可选项 |
| realtime TTS 轻预热 | 已上线 | 压低首段 TTS 准备时间 | 预热失败不应污染主流程 |
| retrieval 瘦身 | 已上线 | 缩短上游准备与首句生成 | 当前 `top_k=1` 是较优点 |
| 首句更短 | 已上线 | 提前触发首段 TTS | 与可懂度需要平衡 |
| 首段切片更激进 | 已上线 | 更早生成第一段可播音频 | 当前 `6~10` 字是有效配置 |
| 录音 `VAD` 提前截断 | 已上线 | 直接降低端到端前置耗时 | 需继续稳态调参 |

## 6. 建议继续推进的优化项

### 6.1 P0：先做网络分层排障，再继续压端到端首字

优先级最高的工作，先确认现场网络是否满足基本可播阈值；阈值不达标时，不应继续把主要精力投入模型与切片微调。

建议动作：

- 固化“同机位 30 次 ping + 30 次 HTTP”一键测试，纳入联调前置步骤
- 要求至少两种接入方式 AB：办公 Wi-Fi 与手机热点
- 每次板端卡顿都必须附带网络测量结果，不再只提交应用日志

在网络基线达标后，再继续压以下两项：

- 录音段时长
- 板端 `prebuffer_wait_ms`

建议动作：

- 继续调 `VAD` 起止阈值，目标是减少“说完后还在等”的尾部静音
- 复测 `DEMO_RECORD_MIN_DURATION_MS` 是否还能安全下调
- 用最近 20 次板端日志统计 `prebuffer_wait_ms` 分布，再决定是否下调 prebuffer

原因：

- 这两段对端到端首字延迟的边际收益最大
- 也是当前最容易造成“云端明明够快，用户还是觉得慢”的地方

### 6.2 P0：把板端预缓冲改成“以日志驱动的动态调参”

当前不建议继续固定调大或调小 prebuffer，而应建立简单规则：

- 稳网场景优先压首字，可用较小 prebuffer
- 弱网场景优先抗抖动，可用较大 prebuffer

建议至少形成两档配置：

- `demo_stable_wifi`
- `demo_weak_wifi`

切换依据可先简单化：

- 最近若干次 `max_gap_ms`
- 最近若干次 `underrun_count`

### 6.3 P1：并行 `intro + /audio` 已上线，下一步先保守扩容与继续观测

这项已经不是“建议实施”，而是**已上线**。当前真实语义是：

- `intro` 播放期间后台并行打开 `/audio` 并收流
- 云端音频先缓存，不抢播
- `intro` 结束后再打开 playback gate，释放到现有播放链路

目前阶段性结论：

- 并行收流本身已命中
- 早期 `wait_timeout` 误判已修正
- 但现场队列峰值仍长期贴顶，因此当前重点不是再改并行语义，而是先留安全余量、继续观察：
  - `receive_queue_peak`
  - `decode_queue_peak`
  - `intro_end_to_first_audio_byte_ms`
  - `open_audio_to_first_audio_byte_ms`

当前更合理的下一步是：

- 先把队列和 jitter 缓冲留出余量
- 再判断并行 `intro` 是否还需要继续做更激进的提前释放策略

### 6.4 P1：进一步约束回答长度，但不要硬裁到影响可用性

当前“总回答约 `25 ~ 35` 字”的方向是对的，因为它同时降低：

- LLM 完整生成时长
- TTS 总时长
- 下行总字节数
- 板端连续播放压力

建议：

- 保持“首句先结论”
- 默认答案控制在 `25 ~ 35` 字
- 不建议先硬压到 `15` 字以内，否则信息密度和可信感会明显下降

### 6.5 P2：标点停顿润色，只作为体验层增强

在 `underrun_count=0` 的前提下，如果主观听感仍偏“机械卡顿”，可以考虑：

- 在逗号、句号等位置小剂量插入静音帧

但这不是当前首字延迟主线工作，应晚于：

- 端到端首字
- 板端预缓冲
- 弱网稳定性

## 7. 不建议当前投入的方向

### 7.1 不建议继续重度优化 LLM 首 token

原因：

- 当前 `first_llm_chunk_ms` 已大幅下降
- 从整体数据看，继续深挖这里的边际收益有限
- 还可能引入回答质量退化和提示词失稳

### 7.2 不建议把慢速播放作为默认链路

`0.8x` 慢速可能改善清晰度，但会直接拉长总时长，放大卡顿感知。  
当前它不符合“更早出声”的目标，应保持为记录项，不进入默认配置。

### 7.3 不建议为了首字延迟大改 `v2` 主链

`v2` 已满足本轮 demo 需求。  
首字延迟优化应继续收敛在 `v3/realtime` 分支，不应反向侵入稳定交付线。

## 8. 推荐执行顺序

建议后续按以下顺序推进：

1. 先做板端首字分段统计固化  
   每次联调都同时记录：
   - `first_audio_byte_local_ms`
   - `intro_end_to_first_audio_byte_ms`
   - `open_audio_to_first_audio_byte_ms`
   - `prebuffer_wait_ms`
   - `underrun_count`
   - `underrun_ms`
   - `max_gap_ms`
   - 云端 `trace.first_audio_byte_ms`

2. 调 `VAD` 与最小录音时长  
   目标是压录音段，而不是动云端。

3. 调 prebuffer 策略  
   目标是在 `underrun_count` 可接受的前提下压缩 `prebuffer_wait_ms`。

4. 在并行 `intro` 已上线的前提下，先扩缓冲余量  
   目标是把 `receive/decode` 队列峰值从长期 `100%` 压到更安全区间，再评估并行收益。

5. 继续做弱网实测  
   包括直连 Wi-Fi、热点中继、会展现场模拟三种场景。

6. 最后再做声学润色项  
   如标点停顿、小剂量填隙。

## 9. 验收标准

建议把验收拆成网络、云端、板端、主观体验四层。

### 9.1 网络基线验收（新增）

- `ping` 丢包率：建议 `<= 5%`（超过该值需先判定为网络风险场景）
- HTTP `jitter`：建议 `< 300ms`（`> 800ms` 基本可判为高抖动网络）
- 若不达标，允许进入“弱网策略档位”验证，但结论不得外推到“代码主链路退化”

### 9.2 云端验收

- `trace.first_audio_byte_ms <= 2500ms` 为目标值
- `production_ratio >= 1.5` 为最低线，`>= 2.0` 为更稳妥目标
- `audio_max_chunk_gap_ms` 在稳网场景下不应持续出现异常长尾

### 9.3 板端验收

- 稳网场景下：
  - `underrun_count = 0`
  - `prebuffer_wait_ms` 明显低于当前基线
  - `intro_end_to_first_audio_byte_ms` 与 `open_audio_to_first_audio_byte_ms` 保持稳定下降或至少不恶化
  - `receive_queue_peak / decode_queue_peak` 不应长期贴满
- 弱网场景下：
  - 允许适度增加 `prebuffer_wait_ms`
  - 但要优先保证 `underrun_count` 不显著恶化

### 9.4 主观体验验收

- 用户触发后应在“可接受的短等待”内听到明确反馈
- 首段回答应先给结论，不应长时间沉默
- 首段起播后，不应频繁出现明显断续

## 10. 最终结论

`20260409_流式传输` 这条线在“云端首包”上已经完成了关键突破：  
当前 `v3/realtime` 不再卡在 `LLM` 首段，也不再卡在“完全拿不到首段音频”。从工程上看，下一步最值得投入的，不是继续小幅压云端 `TTFT`，而是把优化重心转到端到端链路：

- 更短、更稳的录音截断
- 更合理的板端预缓冲
- 更稳的弱网播放表现
- 更准确地区分“首字慢”和“播放卡”

后续所有优化都建议围绕一个核心原则展开：

先用统一指标拆账，再按瓶颈所在层做优化，不再用单一“总耗时变快了”判断方案优劣。
