# 低延迟 VC 流式方案实施方案

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在完全保留现有 `/api/v2/tasks -> 轮询 -> audio_url` 异步链路的前提下，为 `ESP/喵伴` 新增一条基于 `HTTP chunked` 的低延迟 VC 流式语音返回链路。

**Positioning:** 当前 `v2` 设备端闭环已经满足本轮 demo 需求，且已具备稳定交付价值。本实施方案不是替换当前主链路，而是建设一条并行探索线，用于验证“更早出声”的实时体验。

**Architecture:** 服务端新增独立的 `v3/realtime` session 编排层，输入仍然沿用整段 PCM/WAV 上传，ASR 和 RAG 保持现状，LLM 与 TTS/VC 以流式方式串接，并把生成中的裸 `PCM` chunk 直接回传给 ESP。设备端不替换当前 `v2` 逻辑，而是新增一套并行的 realtime client/playback 分支，支持边收边播和显式失败。

**Tech Stack:** FastAPI, DashScope-compatible OpenAI client, requests/httpx, RQ/Redis, ESP-IDF 5.5.4, ESP HTTP Client, ESP-VoCat v1.2, cJSON, FreeRTOS.

---

## 当前稳定基线

实施 `v3/realtime` 前，以下 `v2` 基线已经成立：

- 目标板：`ESP-VoCat v1.2`
- 工具链：`ESP-IDF 5.5.4`
- 现有触发方式：`touch`
- 现有链路：`触摸 -> 固定4秒录音 -> upload -> poll -> download wav -> play`
- 服务器地址：`http://<CURRENT_BASE_URL>`
- 推荐设备 ID：`miaoban-v1p2-001`

已完成并验证过的关键修复：

- 独立 pipeline task，避免 `main` 栈溢出
- `poll` 单次 `ESP_ERR_HTTP_EAGAIN` / `ESP_ERR_TIMEOUT` 可重试
- WAV `data` chunk 长度异常时 clamp 到文件剩余字节数
- WAV 尾部非完整帧时向下裁齐

这些结论意味着：

- `v2` 现在是正式演示和交接线
- `v3/realtime` 的实现必须严格避免影响这条基线

## 实施原则

1. 先服务端、后设备端  
先完成 provider 探测和服务端 smoke，再碰 ESP。

2. 先最小可验证、后体验优化  
先证明“能提前出声”，再谈更高级的实时体验。

3. 任何新模块都不能侵入式改写 `v2` 主链  
`src/api/tasks.py`、`src/workers/pipeline.py`、现有 `tts.py/llm.py` 默认只做最小兼容改动。

4. 保留明确失败  
第一版 `v3` 失败时直接报错，不自动回退到 `v2`。

5. 保留阶段日志  
服务端和 ESP 端都要能看出卡在 `asr/retrieval/llm/tts/stream/playback` 哪一段。

  - 预热失败只写入 `tts_warmup_failed`
  - 不污染主流程状态机
- `realtime_session.py` 首段 TTS 切片改为更激进：
  - 第一段使用 `6` 到 `10` 字阈值
  - 后续仍使用 `8` 到 `40` 字阈值
  - 切片优先使用句末、逗号、顿号、冒号、空格等软边界
  - 若首段超过上限仍无边界，则硬切，保证 TTS 尽早启动
- 板端录音从“固定录满 `4s`”改为“最长 `4s` + 轻量 VAD 提前结束”：
  - 检测到语音后，至少录满 `1000ms`
  - 后续连续静音 `700ms` 即提前结束
  - 未检测到语音时仍录满 `4s`，避免误触立刻上传空音频
- 当前 VAD 是板端轻量能量阈值方案，不是 WebRTC/Silero 这类现成模型：
  - 优点是无新依赖、低 CPU、便于现场调阈值
  - 风险是强噪声环境下可能误判，需要看 `voice_started/max_level/vad_stopped` 日志调参

2026-04-10 深夜 bug11 新增结论：

- 板端日志显示 realtime 音频流请求 `HTTP 200`，但在 header 校验阶段失败：
  - `Missing audio header: Content-Type`
  - `error_code=audio_header_mismatch`
- 根因不是“服务端没回音频”，而是板端 header 读取/校验过严：
  - header key 大小写兼容不足（`Content-Type` vs `content-type`）
  - `Content-Type` 校验只接受完全等值，不接受常见参数化值
- 已在 `esp_idf_demo/main/cloud_client.c` 修复：
  - header 读取改为大小写兼容
  - header 值校验允许 `application/octet-stream; ...` 形式
- 本地 `idf.py build` 已通过，修复可编译落地

因此，`v3` 联调新增一条硬约束：

- 不得假设对端 header key 的大小写形态固定
- 不得把 `Content-Type` 当作必须严格字面等值的字段

2026-04-11 bug13/bug14 后新增结论：

  - `audio_out_write_pcm_chunk_buffered()`

  - 平滑度会提升
  - 但用户体验反馈首播等待仍偏长
  - 因此该调参已撤销
- 后续不应继续盲目加大板端缓冲
- 下一阶段重点改为观测和优化上游生产速度：
  - `realtime_smoke.py` 读取完整 `/audio` 并输出整流统计
  - smoke 增加虚拟播放器欠载计数
  - 服务端 `trace` 增加结构化生产指标
  - 固定 `tc/clumsy` 受限网络条件后再做 A/B

新增观测指标：

- `llm_chunk_count`
- `tts_segment_count`
- `segment_ready_ms`
- `audio_chunk_count`
- `audio_bytes`
- `audio_duration_ms`
- `audio_stream_wall_ms`
- `audio_max_chunk_gap_ms`
- `production_ratio`

判断原则：

- 如果 `production_ratio < 1`，说明平均产音频速度低于播放速度，板端必然可能欠载
- 如果 `audio_max_chunk_gap_ms` 高，说明上游供给不均匀
- 如果 smoke 的 `virtual_player.underrun_count > 0`，说明即使本地网络正常，按当前播放模型仍会欠载
- 这种情况下优先优化 `LLM -> 切片 -> realtime TTS` 的连续供给，而不是继续增加板端等待

## 来自 bug 日志的实施约束

这些不是抽象建议，而是已在当前项目里真实发生过的问题，`v3/realtime` 必须吸收。

### 1. 不能再把长链路压回 `main` 栈

`bug.txt` 暴露过 `main` 栈溢出。`v3` 会比 `v2` 更长、更复杂，因此：

- ESP 侧 realtime pipeline 必须单独任务承载
- 需要可配置任务栈大小
- 新增长链路不应放回 `app_main`

### 2. `asr_empty_text` 要作为常态失败路径设计

`bug2.txt` 证明：

- 链路打通不代表识别一定成功
- 板端音频质量、说话时机、环境噪声都会导致 `asr_empty_text`

因此：

- `v3` 需要明确的 `asr` 失败阶段
- 不能把“没有文本”混成网络失败或 provider 异常
- 失败时要能快速回退或直接结束

### 3. 不要假设云端返回 WAV 头完全可信

`bug4.txt`、`bug7.txt` 证明：

- `data` chunk 长度字段可能异常
- payload 末尾可能不是完整帧

因此：

- realtime 音频播放器必须宽容
- 任何按头部长度严格信任的逻辑都要慎用
- 如果 provider 返回的 chunk 不是标准完整 WAV，优先按流式 PCM/裸音频处理

### 4. 单次网络抖动不能直接等于整条链路失败

`bug6.txt` 证明：

- 单次 poll 请求超时并不代表任务失败

对应到 `v3`：

- 单次 stream read timeout、短暂抖动要有容错设计
- 需要区分“连接已死”和“暂时没数据”
- 不要把所有读超时都直接映射成失败

### 5. 阶段日志必须贯穿到底

当前 `v2` 的板端联调之所以能定位问题，依赖的是清晰的阶段日志。

`v3` 需要保留同样能力：

- 服务端记录 `asr/retrieval/llm/tts/streaming`
- ESP 端记录 `record/upload/session/open-stream/playback`
- 每段都能输出耗时和错误码

### 6. 先 smoke，再上板

当前项目已经证明：如果 provider 格式没摸清就直接上板，问题会被放大且难定位。

因此：

- 先在服务器/本机跑 `realtime_smoke.py`
- 再做 curl/httpx 播放侧验证
- 最后才交给 ESP 边收边播

### 7. 不能把“下载成功”误判成“音频完整”

`bug8.txt` 证明：

- 云端真实音频文件可能有 `1.1MB+`
- 板端旧下载逻辑可能只拿到前 `131KB` 左右
- 结果表现为“流程成功、开始播放、但只播约 `2.7s`”

因此：

- `v3` 不能只依赖“HTTP 200 + 有首包”判断音频拉取成功
- 设备端流式 reader 必须显式记录：
  - 服务端宣称的 `content-length` 或 chunk 流状态
  - 实际累计接收字节
  - 是否完整收流
- 如果继续保留 `v2` 整包下载逻辑，也必须优先使用显式 read loop，而不是只依赖黑盒事件回调

### 8. 大音频会直接撞到板端内存上限

`bug9.txt` 证明：

- 云端单条返回音频可能达到 `1.4MB`
- 当前板端 `DEMO_WAV_DOWNLOAD_MAX_BYTES` 只有 `1MB`
- 当前工程未启用 `PSRAM`
- 因此整包下载大音频时会直接触发 `ESP_ERR_NO_MEM`

因此：

- `v3` 设计必须默认规避“整段音频完整落内存”
- `v3` 的正确方向是：
  - 裸 `PCM` chunk
  - ring buffer / 双缓冲
  - 边收边播
- 即使继续维护 `v2`，也不应假设未来所有音频都能安全整包放进内部 heap

### 9. `status=done` 不等于一定有音频

`bug10.txt` 证明：

- 云端任务可能 `status=done`
- `answer_text` 已成功生成
- 但 `tts_status=failed`
- 最终 `audio_url` 为空

因此：

- `v3` 状态机和错误码不能把“文本成功但音频失败”混成同一种成功
- 服务端要明确区分：
  - `llm done`
  - `tts streaming failed`
  - `audio output unavailable`
- ESP 端看到“无音频可播”时，提示必须更接近真实原因，不能只打印模糊的下载失败

## 验收标准

### 服务端

- `POST /api/v3/realtime/sessions` 可创建 session
- `GET /api/v3/realtime/sessions/{id}` 可看到阶段状态
- `GET /api/v3/realtime/sessions/{id}/audio` 可持续输出 chunk
- `v2` 链路无回归

### 设备端

- 可创建 realtime session
- 可边收边播
- 网络短抖动不立即全链路失败
- realtime 失败时可回退 `v2`

### 体验

- 首字时间明显早于当前 `v2`
- 总体等待体感明显改善

## 当前结论

当前最合理的执行策略是：

- 把 `v2` 当作稳定正式线
- 把 `v3/realtime` 当作并行探索线
- 先做服务端最小可行性验证
- 只有当 provider 行为和首字收益都成立时，再继续推进 ESP 端边收边播
