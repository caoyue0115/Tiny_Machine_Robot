# 低延迟 VC 流式方案计划大纲

日期：`2026-04-09`

## 1. 当前状态

当前项目已经具备一条稳定可演示的 `v2` 异步链路：

- `POST /api/v2/tasks`
- 轮询 `GET /api/v2/tasks/{task_id}`
- 完成后返回 `audio_url`

这条链路当前已经满足本轮 demo 需求，且已经完成以下基线收口：

- `ESP-VoCat v1.2` 板端已跑通 `touch -> 固定4秒录音 -> upload -> poll -> download -> play`
- `ESP-IDF 5.5.4` 已验证构建通过
- `main` 栈溢出已改为独立 pipeline task
- `WAV data chunk` 长度异常和尾部非整帧问题已在板端兼容
- `poll` 单次 `EAGAIN/timeout` 已改为容错重试

因此，`20260409_流式传输` 这条线不是“抢救当前 demo”，而是一条并行探索线，目标是把整体体验往更低延迟方向推进，同时不破坏当前已满足需求的版本。

## 2. 背景与目标

当前 `v2` 链路可用，但整体体感延迟仍然较高，典型总耗时约 `10` 到 `15` 秒，主要耗时集中在：

- `LLM`
- `TTS`

本轮新增一条“低延迟 VC 流式链路”，目标是：

- 面向 `ESP/喵伴` 终端
- 完整保留现有异步方案不变
- 不影响现有 `/api/v2/tasks` 和现有阿里云后端终端
- 在服务端新增并行的实时输出链路
- 让设备更早出声，缩短主观等待时间

## 3. 与 Coze 官方方案的差距

本方案的定位不是短期内完全追平 Coze 官方端到端语音方案，而是把当前 demo 的体验和架构逐步向其靠近。

当前差距主要在：

- 首字时间 `TTFT`
- 实时会话一体化程度
- 边生成边播放的连续性
- 实时语音产品能力，例如中断、续说、流式状态管理

当前项目相对 Coze 的优势仍然成立：

- `RAG` 边界更明确
- provider 更容易替换
- 系统行为更可解释
- 板端、云端、日志链路已经真实打通

因此，本轮目标是先补齐“服务端流式输出 + 板端边收边播”这一层，而不是追求一次性复制 Coze 的完整实时语音产品能力。

## 4. 约束

本轮设计明确遵守以下约束：

1. 现有方案必须完整保留  
当前 `/api/v2/tasks -> 轮询 -> audio_url` 行为不改，老客户端继续可用。

2. 新方案只能并行新增  
不能把现有链路直接改造成流式，避免影响已有调用方。

3. 新方案服务对象是 `ESP/喵伴`  
本轮不优先为网页或 PC 端设计新的实时交互协议。

4. 输入侧不实时化  
ESP 仍然先整段录音、再一次性上传，不做边录边传。

5. 输出侧实时化  
服务端在生成阶段把音频以流的形式尽快返回给 ESP。

6. VC 参考音色固定  
第一版使用服务端预置参考音色，不要求 ESP 端上传或选择音色。

7. 当前 demo 满足需求  
因此本轮实施必须控制风险，优先保证 `v2` 基线不回归。

## 5. 核心方案

### 5.1 现有链路保留

现有异步链路继续保持：

- `POST /api/v2/tasks`
- `GET /api/v2/tasks/{task_id}`
- 返回 `audio_url`

现有 worker、数据库状态、音频文件落盘、轮询逻辑都不作为本轮主要改动对象。

### 5.2 新增独立实时接口

新增一组独立接口，建议使用 `v3/realtime` 命名空间，与 `v2` 完全隔离。

建议接口形态：

- `POST /api/v3/realtime/sessions`
  - 作用：提交整段 PCM/WAV 输入，创建一次实时语音会话
  - 返回：`session_id`、基础状态、后续拉流地址

- `GET /api/v3/realtime/sessions/{session_id}/audio`
  - 作用：按 `HTTP chunked` 拉取服务端边生成边输出的语音流
  - 返回：连续音频 chunk

可选补充接口：

- `GET /api/v3/realtime/sessions/{session_id}`
  - 用于调试查询当前会话阶段、错误信息、trace

### 5.3 传输方式

实时音频返回采用：

- `HTTP chunked`

选择原因：

- 更贴近当前 HTTP 架构
- 对 ESP 端实现相对直接
- 当前输入不是实时上传，不需要 WebSocket 的双向流复杂度

### 5.4 模型策略

本轮计划使用：

- VC/TTS 模型：`qwen3-tts-vc-realtime-2026-01-15`

同时要求：

- LLM 侧：`stream=True`
- TTS/VC 侧：`stream=True`

目标是让服务端在 LLM 产出文本片段后，尽快进入后续语音合成并持续往下游输出。

### 5.5 VC 音色策略

第一版使用：

- 服务端固定预置参考音色

不在本轮做：

- 按设备绑定不同音色
- 客户端上传参考音频
- 每次请求自带音色配置

这样可以降低接口复杂度，优先验证低延迟链路本身。

## 6. 服务端设计

### 6.1 新增 realtime provider / orchestration

建议在现有 `src/providers` 和 `src/api` 体系里新增独立模块，而不是改写现有异步 worker 主链。

建议新增：

- `src/api/realtime.py`
  - 负责 `v3/realtime` 路由

- `src/providers/realtime_tts.py`
  - 负责调用 `qwen3-tts-vc-realtime-2026-01-15`
  - 负责处理流式音频 chunk

- `src/providers/realtime_llm.py`
  - 负责 LLM `stream=True`
  - 负责把文本增量交给后续 TTS/VC 层

- `src/services/realtime_session.py`
  - 负责一次 realtime session 的编排
  - 组织 ASR、检索、LLM stream、TTS stream、chunk 输出

### 6.2 与现有异步链路隔离

现有这条链路尽量不动：

- `src/workers/pipeline.py`
- `src/providers/tts.py`
- `src/providers/llm.py`
- `src/api/tasks.py`

也就是说：

- `v2` 继续走异步任务、落盘文件、返回 `audio_url`
- `v3` 走独立 session、直接流式输出音频

### 6.3 输入处理

新链路的输入建议保持与现有上传契约尽量一致：

- 上传内容：原始 PCM
- 采样率：`16kHz`
- 位宽：`16-bit`
- 声道：`mono`

这样 ESP 侧不需要因为新链路重做录音格式。

### 6.4 ASR 与检索

本轮不优先改 ASR 模式，仍然沿用现有：

- 整段音频识别
- 检索增强

这样能把复杂度聚焦在“回答生成与语音返回”的低延迟上。

### 6.5 LLM 流式输出

新链路里，LLM 要以增量方式产出文本：

- 服务端逐段接收 LLM token / 文本块
- 在合适的分段点把文本片段送入 TTS/VC

需要额外设计：

- 文本分段策略
- 避免每个 token 都立即触发一次 TTS
- 在延迟和语义完整性之间取平衡

### 6.6 TTS/VC 流式输出

TTS/VC 层需要：

- 接收来自 LLM 的增量文本片段
- 使用固定参考音色
- 返回可逐步输出给 ESP 的音频 chunk

服务端最终需要把这些 chunk 以 `HTTP chunked` 形式写给客户端。

## 6.7 当前阶段收口

截至 `2026-04-10` 晚间，这条计划线已经不再停留在“设计中”。

已实质完成：

- `v3/realtime` 服务端接口
- LLM `stream=True`
- realtime TTS 主链路接入
- `response.audio.delta` 解码与统一 PCM 格式转换
- 远端部署与 smoke
- `TTFT` 优化 A/B

当前远端最好实测：

- `first_llm_chunk_ms: 2642`
- `first_tts_chunk_ms: 3314`
- `first_audio_byte_ms: 3314`
- `done_ms: 6861`

因此，这份计划的下一阶段重点已从“继续服务端可行性验证”转为“板端云端联调与体验校准”。

## 7. ESP 端设计

### 7.1 保留现有模式

当前 `esp_idf_demo` 的现有模式继续保留：

- 触摸
- 固定时长录音

### 7.2 当前建议的联调目标

现在可以把重点放在新增一条并行 `v3/realtime` 分支，而不是再继续改现有 `v2`。

联调优先级：

1. 先让 ESP 端稳定跑通：
   - 上传原始 PCM
   - 建立 `/audio` 连接
   - 边收边播
2. 再对齐板端与云端指标：
   - 服务端 `first_audio_byte_ms`
   - 板端 `first_audio_byte_local_ms`
   - 板端 `playback_start_ms`
3. 最后再根据板端实际表现决定是否继续压服务端 `TTFT`

当前判断：

- 云端已经足够进入板端联调
- 不必等待服务端先压到绝对 `3s` 再开始板端工作
- bug13/bug14 后补充：
  - 板端基础 jitter buffer 有效
  - 继续加大预缓冲会增加用户等待感
  - 下一步应优先观测上游生产速度，而不是继续扩大板端 buffer
  - 关键指标：`production_ratio`、`audio_max_chunk_gap_ms`、`virtual_player.underrun_count`
- 上传
- 轮询
- 下载 WAV
- 播放

### 7.2 新增 realtime mode

建议新增一个并行模式，而不是覆盖现有实现。

建议形态：

- 继续整段录音上传
- 改调新的 `v3/realtime` 创建接口
- 然后连到 `audio chunked stream` 接口
- 一边接收，一边播放

### 7.3 设备端最小新增能力

ESP 端需要补的能力：

- 处理新的 realtime session 创建响应
- 建立并保持一个音频流式下载连接
- 支持边接收边播放
- 处理流中断和异常回退

### 7.4 回退策略

如果 realtime 模式失败，建议允许：

- 返回错误
- 或者回退到现有 `v2` 异步链路

是否做自动回退，可以在实现阶段再定；但计划中应预留这个策略。

## 8. 兼容策略

本轮兼容要求如下：

1. 现有 `/api/v2/tasks` 行为不改
2. 现有数据库和任务状态机制不要求重构
3. 现有 `audio_url` 方案不删除
4. 现有阿里云后端终端继续走老链路时不受影响
5. 新低延迟链路通过独立 `v3/realtime` 命名空间进入
6. 当前板端稳定版本继续可打包、可演示、可交接

## 9. 风险

### 9.1 模型层风险

- `qwen3-tts-vc-realtime-2026-01-15` 的实际流式调用方式与现有 TTS provider 差异可能较大
- LLM stream 和 TTS stream 串接时，文本分段可能影响音频自然度

### 9.2 服务端实现风险

- `HTTP chunked` 输出过程中，异常中断后的资源清理要明确
- realtime session 可能需要内存缓冲，需控制会话数量和缓冲尺寸

### 9.3 ESP 端风险

- 边收边播对缓冲要求更高
- 网络抖动可能导致播放卡顿
- 音频 chunk 边界不合理可能影响播放连续性

### 9.4 兼容风险

- 如果复用现有 provider 代码过深，容易误伤老链路
- 因此必须坚持“独立接口、独立 session、独立 provider”的边界

### 9.5 已知 bug 经验对应的实现风险

- 不要把新长链路压回 `main` 任务栈
- 不要假设云端返回音频头完全可信
- 不要把单次 HTTP 抖动直接等价成整条链路失败
- 不要跳过阶段日志，否则后续联调很难定位问题

## 10. 验收标准

### 10.1 兼容性验收

- 现有 `/api/v2/tasks` 链路功能无回归
- 现有 ESP 轮询 + `audio_url` 流程继续可用

### 10.2 新链路可用性验收

- 可成功创建 realtime session
- ESP 可拉取连续音频 chunk
- ESP 可边收边播，不必等完整音频生成后再播放

### 10.3 体验验收

- 相比当前 `10-15s` 体感等待，新链路明显更快开始出声
- 首包音频时间显著早于旧链路完整音频落盘时间

### 10.4 运维验收

- 新链路失败时可定位到明确阶段
- 不影响现有异步链路的健康检查和日常运维

## 11. 建议实施顺序

### Phase 1: 方案验证

- 确认 `qwen3-tts-vc-realtime-2026-01-15` 的实际 API 调用方式
- 验证 LLM `stream=True` 与 TTS `stream=True` 的最小串接可行性
- 先完成服务端 smoke，不接板

2026-04-10 进展补充：

- `LLM stream=True` 已验证有效，远端 `v3` smoke 中：
  - `first_llm_chunk_ms` 从 `4563ms` 降到 `2316ms`
- 当前 `TTS` 仍是主瓶颈：
  - `first_tts_chunk_ms` 仅从 `9010ms` 降到 `8389ms`
- 已确认 `qwen3-tts-vc-realtime-*` 不走现有 HTTP TTS 接口
- DashScope SDK 已提供 `qwen_tts_realtime` 实现，第一版可直接基于 SDK 做 probe
- 已确认 realtime 回调事件是 JSON，音频块在 `response.audio.delta.delta` 中以 base64 形式返回
- 已新增：
  - `scripts/realtime_tts_probe.py`
  - `src/providers/realtime_tts.py`
- 当前阻塞点不是事件格式，而是音色匹配：
  - 现有 `voice_id` 在 `qwen3-tts-vc-realtime-2026-01-15` 下返回 `CLIENT_ERROR`
  - 高概率原因是该音色不是为 realtime 目标模型创建
- Phase 1 继续推进前的前置条件：
  - 先准备一个为 `qwen3-tts-vc-realtime-2026-01-15` 创建的专用 `voice_id`
  - 然后再做第二轮 provider probe

### Phase 2: 服务端独立原型

- 新增 `v3/realtime` 路由
- 新增 realtime session 编排
- 跑通从整段输入到 chunked 音频输出

### Phase 3: ESP 端接入

- 在 `esp_idf_demo` 增加 realtime mode
- 跑通边收边播

### Phase 4: 回退与验收

- 完善错误处理
- 验证 `v2` 无回归
- 做延迟对比测试

## 12. 本轮结论

本轮建议不是替换现有链路，而是在当前系统旁边新增一条独立低延迟链路：

- 旧链路：继续稳定服务现有终端，也是当前 demo 正式交付线
- 新链路：面向 `ESP/喵伴` 的并行探索线，通过 `HTTP chunked` 实现更快出声

这是当前风险最可控、也最符合项目状态的方案。
