# 2026-04-13 下行音频解耦设计稿

## 1. 背景

当前 `v3 realtime` 下行链路已经切到：

- 公网远端已支持 `audio_format=opus`
- 公网远端已支持 `audio_packetization=framed-v1`
- 板端已支持 `legacy` / `framed-v1` 解析
- 板端已支持 `pcm` / `opus` 协商与解码

但现场 bug 说明当前结构仍存在两个核心问题：

1. 旧问题：`HTTP read -> enqueue -> playback` 串行链路中，播放反压会直接拖慢收流，表现为：
   - `max_enqueue_ms` 很高
   - `max_inter_chunk_gap_ms` 与 `max_enqueue_ms` 高度接近
   - `underrun_count / underrun_ms` 偏高

2. 新问题：命中 `Opus + framed-v1` 后，板端在 `stream_audio` 刚开始时出现 `StoreProhibited` 崩溃（`bug31`），说明：
   - 新链路已经真正命中
   - 但收流、解析、解码、播放仍耦合在同一条任务路径中
   - 在 ESP32-S3 上，这种做法的栈/内存/时序风险偏高

因此需要从“继续在串行链路上补丁”切到“结构性解耦”。

## 2. 目标

本设计稿目标不是一次性做成小智的完整架构，而是先做一版能稳定落地的第一阶段解耦：

- 把下行链路拆成 `receive -> decode -> playback`
- 不再在 `pipeline` 任务里直接做 Opus 解码
- 不再让网络收流直接被播放 ringbuffer 反压阻塞
- 保留现有 `PCM fallback`
- 保留现有日志口径，并新增更细的队列观测

本阶段不做：

- 更换 HTTP 协议为 WebSocket / UDP
- 改动上行录音或 VAD 状态机
- 完整照搬小智的全部音频服务架构
- 在本阶段就引入复杂的丢包补偿或 PLC 策略

## 3. 推荐方案

推荐采用三段式任务模型：

1. `receive task`
   - 负责：
     - `esp_http_client_read`
     - `legacy` / `framed-v1` 解析
     - 将下行“音频包”投递到接收队列
   - 不负责：
     - Opus 解码
     - 直接写播放 ringbuffer

2. `decode task`
   - 负责：
     - 从接收队列取包
     - 若为 `opus`，做 Opus 解码
     - 若为 `pcm`，直接透传
     - 将输出 PCM 投递到播放队列
   - 不负责：
     - HTTP 收流
     - 直接驱动 codec 写出

3. `playback task`
   - 负责：
     - 从播放队列取 PCM
     - 维持 jitter/prebuffer
     - 调用现有 `audio_out_write_pcm_chunk()` 写出

一句话概括：

`HTTP/network 压力`、`codec/decode 压力`、`speaker/playback 压力` 分开。

## 4. 数据流

### 4.1 Opus 路径

`HTTP read`
-> `framed-v1 parser`
-> `encoded_packet_queue`
-> `opus decode`
-> `pcm_packet_queue`
-> `audio_out jitter/playback`

### 4.2 PCM 路径

`HTTP read`
-> `legacy/framed parser`
-> `encoded_packet_queue`
-> `decode task direct passthrough`
-> `pcm_packet_queue`
-> `audio_out jitter/playback`

这样做的价值是：

- `receive` 任务不再因为本地 speaker 卡顿而阻塞很久
- `decode` 任务可以单独给更大的栈
- 未来若需要进一步优化，还可以单独替换某一段，而不是整条链路一起动

## 4.3 启动顺序约束

第一版必须明确任务间同步的启动顺序，避免出现“`decode task` 已启动，但队列尚未创建”的错误。

启动顺序约束（第一版）：

1. 创建 `encoded_queue / pcm_queue`
2. 创建 `decode_task`
3. 创建 `receive_task`（或由 `pipeline` 触发其启动）
4. 不要求在启动时预填充任何队列

补充要求：

- `decode_task` 启动时必须断言两个队列都已创建
- `receive_task` 启动时必须断言 `encoded_queue` 已创建
- 若任一关键资源创建失败，`pipeline` 直接进入失败收尾，而不是部分启动后继续运行

## 5. 队列与边界

### 5.1 编码包队列

新增一条“编码包队列”，元素形态建议为：

- `type`：`PACKET / EOF / ERROR`
- `seq`
- `payload_len`
- `audio_format`
- `packetization`
- `payload bytes`

要求：

- `receive task` 只追加完整包，不投半包
- 不要用 `payload_len=0` 之类的魔法值表示 EOF
- 队列满时必须有显式策略：
  - 第一版不做静默丢包
  - 第一版不做无限阻塞等待
  - 第一版统一走“显式失败并收尾”

理由：

- 现在还在定位主问题阶段
- 静默丢包会让问题更难诊断

当 `encoded queue` 满时，第一版统一语义为：

- 记一次 `receive_queue_full_count++`
- `receive task` 停止继续读取 HTTP
- 向下游发送 `ERROR` 控制事件
- 进入统一收尾流程

### 5.1.1 内存与所有权约定

编码包与 PCM 包都必须以“完整包对象”形式在任务间传递，不允许传递指向临时栈 buffer 的引用。

对象一旦成功入队，所有权即转移给消费方；消费方在处理完成后负责释放。

第一版明确约定：

- `receive task` 产出的 `encoded packet` 必须是完整、独占所有权的对象
- 一旦成功 enqueue 到 `encoded queue`，对象所有权转移给 `decode task`
- `decode task` 完成处理后负责释放 `encoded packet`
- `decode task` 产出的 `pcm packet` 也必须是完整、独占所有权的对象
- 一旦成功 enqueue 到 `pcm queue`，对象所有权转移给 `playback/audio_out`
- 播放完成后由消费方释放

第一版不允许通过共享可变缓冲区在 `receive / decode / playback` 三段之间隐式复用数据，以避免：

- double free
- 提前 free
- 栈上临时 buffer 被异步任务继续引用
- 队列里出现野指针

进一步约束实现方式：

- 第一版队列入队统一使用“动态分配 + 传指针 + 消费方 free”模式
- 明确禁止在栈上定义包结构体后直接把其地址入队

推荐示例：

```c
// 正确：动态分配对象，成功入队后转移所有权
encoded_packet_t *pkt = malloc(sizeof(encoded_packet_t));
pkt->data = malloc(len);
memcpy(pkt->data, data, len);
xQueueSend(encoded_queue, &pkt, timeout);

// 消费方负责释放
encoded_packet_t *pkt = NULL;
xQueueReceive(encoded_queue, &pkt, portMAX_DELAY);
free(pkt->data);
free(pkt);
```

### 5.2 PCM 包队列

新增一条“PCM 包队列”，元素形态建议为：

- `type`：`PACKET / EOF / ERROR`
- PCM 字节块
- 对应 `seq`
- `duration_ms`
- 解码耗时

要求：

- `decode task` 只向播放队列投完整 PCM chunk
- `playback task` 只从 PCM 队列取数据并写现有 jitter/playback

当 `pcm queue` 满时，第一版统一语义为：

- 记一次 `decode_queue_full_count++`
- `decode task` 不再继续阻塞等待
- 向下游发送 `ERROR` 控制事件
- 进入统一收尾流程

第一版同样不做静默丢包，不做“阻塞等待到天荒地老”。

### 5.3 保留现有 jitter ringbuffer

第一版不建议把 `audio_out` 全部推倒重写。

更稳妥的做法是：

- 保留当前 `audio_out` 内部的 jitter/prebuffer/playback task
- 但让它只处理“已解码 PCM”
- 不再承担网络收流或 Opus 解码职责

这样可以减少本轮改动面。

## 6. 控制面与数据面

本设计除了拆数据流，还必须明确“控制面”和“数据面”的分离。

- 数据面：
  - `encoded packet`
  - `pcm packet`
- 控制面：
  - `EOF`
  - `ERROR`
  - `STOP/CANCEL`
  - `TIMEOUT`

第一版最小控制语义：

- 任一 task 失败时，必须向下游发送失败终止信号
- 上游失败不等于直接强杀下游任务
- 下游收到 `ERROR` 后执行本地收尾，而不是继续等待正常 EOF

推荐第一版行为：

- `encoded queue` 收到 `ERROR`
  - `decode task` 不再处理新包
  - 直接向 `pcm queue` 转发 `ERROR`
- `pcm queue` 收到 `ERROR`
  - `playback task` 停止继续接收新 PCM 包
  - 允许把已经进入 `audio_out jitter` 的数据在一个短窗口内尽量 drain
- 最终由 `pipeline` 统一输出 summary

这样做的目标是：

- 避免上游出错后下游永远阻塞
- 避免 pipeline 提前回 `idle`，而下游任务还挂着

## 7. 任务与栈建议

参考小智的做法，Opus codec 应单独放任务。

第一版建议：

- `receive task stack`：`6144 ~ 8192`
- `decode task stack`：`24576`
- `playback task`：先复用现有 `audio_out` 内部任务
- `pipeline task`：从现在的“重处理任务”退化为“流程协调任务”

其中最关键的是：

- `decode task` 单独拿大栈
- 避免 `pipeline task` 继续承载 Opus 解码

第一版还要把运行时内存峰值写清楚，避免后续把堆问题误判成协议问题：

- `decode task` 任务栈：约 `24KB`
- `micro-opus` 伪栈：约 `120KB`（堆）
- Opus 解码器状态：约 `30KB ~ 50KB`（堆，按库实现浮动）

因此第一版要求：

- 板端必须确保 PSRAM 已启用
- 进入 `decode task` 前应有足够可用堆 / PSRAM
- 保守目标是保留至少 `256KB` 可用空间用于解码路径

同时补一条硬约束：

- `receive task` 不做重 CPU 操作
- `receive task` 不做 Opus 解码
- `receive task` 不做播放节奏控制
- `receive task` 不做复杂日志聚合

`receive task` 的唯一目标就是：

- 尽快把网络字节转换为完整音频包
- 尽快把包交给 `encoded queue`
- 立刻脱手

这样才能避免网络路径再次被本地播放路径反压拖慢。

## 8. Decode 任务硬约束

第一版 `decode task` 增加两条硬约束：

1. 一次只做一个 packet 的 decode 生命周期

- codec state 可以常驻
- 但 packet input / pcm output buffer 生命周期按包隔离

这样可以降低对象生命周期复杂度，也便于定位具体是哪一个包触发问题。

2. `decode task` 不直接碰 `audio_out`

- `decode task` 的唯一输出是 `pcm queue`
- 第一版不允许 `decode task` 直接调用：
  - `audio_out_write_pcm_chunk()`
  - `audio_out_write_pcm_chunk_buffered()`

这条约束是为了防止后续为了“先修一下”又把耦合偷偷补回去。

## 9. 收尾语义

第一版必须把收尾顺序写死：

1. `receive task` 结束，并给编码包队列发 EOF
2. `decode task` 消耗完编码包队列后，向 PCM 队列发 EOF
3. `playback task` 消耗完 PCM 队列并 drain 完 jitter ringbuffer
4. 输出统一 summary
5. pipeline 返回并回 `idle`

要求：

- 不允许“上游 done 了，但下游 task 还挂着”
- 保留 close timeout，但 timeout 只作为保护，不作为常态

补充一条责任边界：

- `pipeline` 是协调者，负责等待 `receive / decode / playback` 的退出结果并汇总 summary
- `pipeline` 不重新接管这些任务内部的重处理逻辑

也就是：

- `pipeline` 负责 orchestration
- 不再负责 heavy work

### 9.1 Pipeline 等待退出语义

`pipeline` 虽然退化为协调者，但必须明确等待顺序和超时。

推荐伪代码：

```c
esp_err_t pipeline_wait_stop(void) {
    // 1. 通知 receive_task 停止接收新数据
    // 2. 等待 encoded_queue 被 decode_task 消费空（或超时）
    // 3. 等待 decode_task 退出（或超时）
    // 4. 等待 pcm_queue 被 playback_task 消费空（或超时）
    // 5. 等待 playback_task 退出（或超时）
    // 6. 汇总所有指标并输出 summary
}
```

要求：

- 每个等待步骤都必须有超时
- 超时后必须能进入强制清理
- 第一版可以复用现有 close timeout 体系，但不能无限等待

### 9.2 Receive 停止语义

`receive task` 的停止语义也必须写死。

第一版推荐内部状态：

```c
typedef enum {
    RECEIVE_RUNNING,
    RECEIVE_DRAINING,
    RECEIVE_STOPPED,
} receive_state_t;
```

第一版简化规则：

- 一旦进入终止流程，`receive task` 不再尝试恢复
- 队列满、HTTP 错误、上游 cancel、pipeline stop 都会使其转入停止路径
- 进入停止路径后，`receive task` 直接退出，不再继续读取新音频数据

## 10. 队列容量原则

第一版即使暂不把数字完全写死，也要先写 sizing 原则：

- `encoded queue`
  - 按若干 Opus 帧包估算
  - 目标是覆盖短时 decode 抖动
- `pcm queue`
  - 按若干百毫秒到约 1 秒的 PCM 可播时长估算
  - 目标是覆盖 speaker/playback 抖动
- 第一版优先保守取值
- 后续根据 `*_queue_peak` 与 `*_queue_full_count` 调整

这样实现阶段就不会拍脑袋决定队列大小。

## 11. 观测与日志

本设计第一版必须保留并新增这些指标：

### 8.1 已有指标继续保留

- `audio_format`
- `audio_packetization`
- `packet_count`
- `seq_gap_count`
- `first_chunk_ms`
- `max_inter_chunk_gap_ms`
- `max_enqueue_ms`
- `avg_enqueue_ms`
- `underrun_count`
- `underrun_ms`

### 8.2 新增指标

- `receive_queue_peak`
- `receive_queue_full_count`
- `decode_queue_peak`
- `decode_queue_full_count`
- `decode_packet_count`
- `decode_fail_count`
- `decode_avg_ms`
- `decode_max_ms`
- `pcm_queue_drain_ms`
- `receive_block_ms` 或 `http_read_gap_ms`

目的：

- 分清是网络慢、解码慢，还是播放慢
- 不再把所有问题混成 `max_inter_chunk_gap_ms`

其中：

- `pcm_queue_drain_ms`
  - 表示从 `decode EOF` 到 `playback` 真正 drain 完 `pcm queue + jitter` 的时间
  - 用于定位“为什么 close 很慢”

- `receive_block_ms` 或 `http_read_gap_ms`
  - 用于区分：
    - 网络层没来数据
    - 本地线程没及时处理收到的数据
  - 如果实现阶段发现和现有 `enqueue_ms` 高度重叠，可后移到下一版

## 12. 风险与取舍

### 9.1 收益

- 高概率消除 `bug31` 这类“新链路首包即崩”的风险
- 高概率缓解“HTTP 收流被本地播放反压拖慢”的老问题
- 为后续继续接近小智架构打好边界

### 9.2 风险

- 第一版的 close/drain 处理容易出新边角 bug
- 队列大小如果估得太小，可能出现新瓶颈
- 如果 decode task 太慢，问题会从“播放反压”转成“解码队列积压”

### 9.3 为什么仍推荐做

因为当前问题已经证明：

- 串行链路补丁只能暂时缓解
- 不能从结构上解决收流、解码、播放的耦合

另外需要明确一点：

- 第一阶段重构的主要工程目标之一，就是把 `bug31` 这类崩溃从“难定位的串行链路栈内崩溃”
- 转成“可以归因到具体 `task / queue / decode stage` 的失败”

这也是这轮重构值得做的核心原因之一。

## 13. 分阶段落地建议

建议按两步走：

### 第一步：最小结构性改造

- 新增 encoded queue
- 新增 decode task
- pipeline 只负责发起收流
- audio_out 保持现状
- 跑通 `opus + framed-v1`
- 收集新指标

目标：

- 先稳定，不再崩
- 先能测出解码和播放的边界

### 第二步：进一步向小智靠拢

- 让 playback/jitter 观测更细
- 明确 receive/decode/playback 各自的 backpressure 策略
- 视情况再决定是否把更多逻辑迁进统一 audio service

## 14. 结论

推荐执行本设计的第一步版本。

原因不是“追求架构漂亮”，而是当前 `bug31` 和此前多轮卡顿都在说明同一件事：

- 下行网络收流
- Opus 解码
- PCM 播放

这三件事继续耦合在一条任务路径里，风险过高。

从当前工程状态看，最值得做的不是继续补协议细节，而是先把这三段链路拆开。
