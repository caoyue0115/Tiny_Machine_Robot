# 2026-04-13 卡顿问题处理简报

## 1. 当前结论

本轮卡顿问题不是单点故障，而是分阶段逐步收敛出来的：

1. 早期主因是板端播放链路反压，表现为：
   - 音频已到板端
   - 但入播放队列阻塞严重
   - 导致收流被拖慢
   - 最终出现欠载、卡顿、收尾异常

2. 中期又确认了一层部署问题：
   - 本地调试实例与公网实例不是同一套服务
   - 导致现场一直在跑旧的 `PCM/legacy` 路径

3. 当前最新状态是：
   - 公网已经切到 `Opus + framed-v1`
   - 板端主链路已经能跑通
   - 剩余问题已收敛到收尾尾差和缓冲余量不足

## 2. 主要处理动作

本轮采取了四类关键动作：

### 2.1 先把问题“看清楚”

- 给板端增加了更细的串口日志
- 给云端增加了协商日志
- 新增 `audio_format`、`audio_packetization`、`seq_gap_count`
- 后续又新增了：
  - `receive_queue_peak`
  - `receive_queue_full_count`
  - `decode_queue_peak`
  - `decode_queue_full_count`
  - `decode_packet_count`
  - `decode_fail_count`
  - `decode_avg_ms`
  - `decode_max_ms`
  - `pcm_queue_drain_ms`

这样做的目的，是把“卡顿”从主观感觉变成可以分层定位的数据问题。

### 2.2 解决部署错位

- 发现公网 `OLD_PUBLIC_ENTRY_DISABLED` 不是本地这台 docker
- 确认了真实远端部署目录和容器
- 把最新代码同步到远端
- 打开远端 `REALTIME_AUDIO_ENABLE_OPUS=true`

结果：

- 公网最终切通：
  - `audio_format=opus`
  - `audio_packetization=framed-v1`

### 2.3 解决板端新链路首包崩溃

在 `bug31` 阶段，板端一命中新链路就 panic。

为此做了两类止血：

- 把 `stream_audio` 路径里的大对象从栈搬到堆
- 提高 `pipeline` 任务栈，并补栈水位日志

结果：

- panic 消失
- 新链路可以继续往下跑

### 2.4 做第一阶段音频链路解耦

把板端下行从原来的串行路径改成：

`receive -> decode -> playback`

具体动作：

- 新增 `encoded_queue`
- 新增 `pcm_queue`
- 新增 `decode task`
- 新增 `playback task`
- 明确 `PACKET / EOF / ERROR` 控制语义

结果：

- 原来“命中新链路即崩溃”的问题，被收敛成“队列满导致失败”
- 再通过扩大队列和延长等待时间，把“队列满”也压住

## 3. 当前阶段性结果

从最新的 `bug33` 看，已经有成功样本表现为：

- `stage=stream_audio event=done`
- `pipeline result=ok`
- `audio_format=opus`
- `audio_packetization=framed-v1`
- `receive_queue_full_count=0`
- `decode_queue_full_count=0`

这说明主链路已经基本打通。

当前剩余问题主要集中在：

- 收尾阶段只剩极小尾差时，close 仍可能等超时
- 队列峰值占用率很高，系统仍处于“临界稳定”

最新已增加尾差容忍收尾逻辑，用于消除这类“主链路成功但被收尾误判失败”的情况。

## 4. 这次是如何解决卡顿的

简单说，不是靠单一“调参数”解决，而是按这四步推进：

1. 先把卡顿从“主观感觉”变成“可观测问题”
2. 排除部署路径和旧实例干扰，确保现场真的跑到新链路
3. 用 Opus 降低下行压力
4. 把板端下行链路拆层，避免收流、解码、播放互相拖死

所以这次“解决卡顿”的核心经验不是某一个参数，而是：

- **先定位层次**
- **再切对实例**
- **再压带宽**
- **最后做链路解耦**

## 5. 下一步

当前最重要的下一步不是继续大改，而是验证最新 `v11`：

- 如果 `v11` 能把收尾误失败也抹掉，就说明主链路已经基本站住
- 后续再做的是：
  - 增加缓冲余量
  - 优化收尾
  - 再考虑开场音并行等体验优化
