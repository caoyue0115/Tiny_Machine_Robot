# 实地网络与流式音频测量手册

适用对象：现场硬件联调同事  
目标：判断“语音断续/未播完”是否由现场网络链路导致  
云服务地址：`http://<CURRENT_BASE_URL>`

## 1. 测试前准备

1. 确认设备与测试电脑在同一现场网络环境（同 AP/同路由）。
2. 确认服务器可访问：
```bash
curl -sS http://<CURRENT_BASE_URL>/healthz
```
3. 进入项目目录：
```bash
cd /home/aitopia/Engineering_Projects/.worktrees/religion-demo-20260407/20260407_宗教大模型云服务器Demo
```

## 2. 网络基线测试（ICMP）

执行：
```bash
ping -c 30 -i 0.2 <CURRENT_HOST>
```

记录以下三项：
- `packet loss`
- `rtt avg`
- `mdev`

判定参考：
- `packet loss > 0%`：存在丢包风险。
- `mdev > 40ms`：抖动偏大，可能引发流式断续。
- 出现明显跳变（如几十毫秒到几百毫秒）：链路不稳定。

## 3. 实时链路压测（核心）

执行 5 轮：
```bash
for i in 1 2 3 4 5; do
  echo "--- run_$i ---"
  BASE_URL=http://<CURRENT_BASE_URL> \
  python scripts/realtime_smoke.py ./data/output/demo_test_question_24k.wav \
    --stream-mode immediate --max-polls 60 --audio-timeout 60
done
```

每轮关注 `audio` 事件中的字段：
- `production_ratio`
- `max_inter_chunk_gap_ms`
- `avg_inter_chunk_gap_ms`
- `virtual_player.underrun_count`
- `virtual_player.underrun_ms`

判定参考：
- `production_ratio < 1.0`：产流慢于播放，极易卡顿。
- `max_inter_chunk_gap_ms > 1000`：大概率出现明显断续。
- `underrun_count > 0`：播放器已发生缺料。
- 多轮都出现上述现象：网络/链路问题概率高。

## 4. 板端串口日志抓取（必须）

在板端复现时，抓完整串口日志，重点保留以下行：
- `stage=stream_audio event=done elapsed_ms=...`
- `max_inter_chunk_gap_ms=... avg_inter_chunk_gap_ms=...`
- `realtime_audio_summary ... underrun_count=... underrun_ms=...`
- `pipeline result=...`

建议每次测试至少保留 3 次完整回合日志。

## 6. 结论规则

- 若 PC 压测稳定（`underrun_count=0`、`max_gap` 小）但板端卡顿：优先排查板端 Wi-Fi/任务调度/音频缓冲。
- 若 PC 压测也不稳定：优先判定为现场网络链路问题。
